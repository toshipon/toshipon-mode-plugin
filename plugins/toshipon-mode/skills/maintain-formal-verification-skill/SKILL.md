# Maintain a formal verification skill

形式的なチェックは、それが記述するものの性質を証明する。コードが変わって検証が変わらないと、チェックはもう存在しないコードを記述したまま通り続けることがある。その pass が危険である。証明のように見えるからだ。この skill は、`/toshipon-mode:create-formal-verification-skill` が生成した verify skill、または名指ししたコードに対して model checker・prover・コード上の verifier を走らせる任意の project-local skill の保守ループである。その project-local skill は、agent がそれを使いながら行う変更を扱う。この skill は、それを素通りした変更を扱う。merge、skill を使わずに行った編集、多数の commit にまたがって積もったずれである。

## 結果

各チェックに結果を 1 つ与え、どれかを言う。

- **in sync**: 前回の同期以降、チェックが記述するものを変える変更はなく、チェックは通る。
- **updated**: コードが変わり、検証は新しいコードを記述するようになり、チェックは通る。
- **bug**: 検証は今のコードを記述しており、コードが性質を破る。これはコードについての発見であり、ずれではない。
- **blocked**: チェックをコードに合わせ直せなかったか、実行できなかった。理由を正確に言う。

1 つのチェックが updated かつ bug になることがある。更新で検証が再びコードを記述するようになり、そのうえで性質が失敗する場合である。

## 編集範囲

編集するのは検証だけにする。モデル、harness、性質のファイル、verify skill そのものである。ユーザーが頼まない限り、実行中にプロダクトコードを編集しない。今のコードで性質が失敗したとき、通すために性質やモデルを弱めない。失敗を報告する。

## 手順

1. **チェックを見つける。** verify skill に決まった名前はないので、何をするかで探す。名指ししたコードに対して model checker、prover、その他の verifier を走らせる project skill である。見つけたもの、またはユーザーが名指ししたものをそれぞれ読む。各チェックについて、性質、覆うコード、上限と仮定、実行コマンド、コードを記述していると最後に確かめた commit を集める。verify skill がなければ止まり、`/toshipon-mode:create-formal-verification-skill` を案内する。skill が同期 commit を記録していなければ、検証ファイルを最後に変えた commit を使い、そうしたと言う。

2. **そのまま実行する。** 何かを変える前に各チェックを一度実行し、結果を記録する。ここでの pass は、コードが正しいことを示さない。古い記述がまだ成り立つことを示すだけである。ここでの失敗は、ずれかバグのどちらかである。手順 5 までどちらかを決めない。

3. **覆われたコードへの変更をすべて読む。** 同期 commit から今の commit まで、覆われたファイルの diff を取り、各 commit メッセージを読む。移動したコードも探す。名前が変わった、分割された、別ファイルに移った覆われた関数は、まだ覆われたコードである。チェックが守る状態に触れる新しいコードも探す。同じフィールドに書き込む新しい関数などである。変更ごとに、次のどれかを決める。
   - **影響なし。** 書式、コメント、検証が覆わないコード経路など、検証が記述するものを何も変えない。commit メッセージではなく、モデルや harness に照らして確かめる。
   - **検証がもうコードを記述していない。** 1 つの不可分な操作だったものが 2 つになった、分岐が足された・消えた、チェックが移動した、守られた状態に新しい経路で届くようになった、値の範囲が変わった。モデルか harness を変えなければならない。
   - **約束を意図して変えた。** 変更がコードの約束を変え、それが意図されたことを変更の中の証拠が示している。doc comment、テスト、changelog、commit メッセージである。性質を変えなければならず、その証拠を引用する。
   - **約束が破れているかもしれない。** コードが変わり、約束が変わったことを示す証拠がない。その後に続く失敗はバグ候補として扱う。

4. **結果ではなくコードから更新する。** 変わった各部分が再びレビュアーの開けるコードを指すようにモデルか harness を変え、コードの 1 つの不可分な手順を検証でも 1 つの手順に保つ。再実行の前にコードから更新を書き、チェックを通すものに合わせて形を決めない。性質を変えるのは、約束を意図して変えたときだけにする。古い文言、新しい文言、証拠を書き残す。変更によって上限が誤りにならない限り、上限は保つ。上限を下げるなら報告でそう言う。

5. **再実行し、各結果を判定する。**
   - **pass:** チェックは、失敗する力を失った記述の上で通っているかもしれない。性質が防ぐやり方で新しいコードを壊し（新しいチェックを外す、新しい手順を入れ替えるなど）、チェックが捕まえることを確かめる。その後、壊した変更を捨てる。
   - **fail:** 反例を実際のコードに対して 1 手ずつ再生する。コードで起こり得ない手順があれば、検証が誤っている。検証を直し、何が誤っていたかを言う。すべての手順が起こり得るなら、それはバグである。それを持ち込んだ commit を名指しし、反例をコードの言葉の手順の列として語り、害を 1 文で述べる。実際のコードに対する安いテストや再現でバグを示せるなら、証拠として報告に添える。プロダクトコードには commit しない。

6. **verify skill を更新する。** 各チェックが覆うコード、コマンド、上限、仮定、同期 commit を更新する。同期 commit は確かめた commit にする。blocked のチェックの同期 commit は進めず、報告でそう言う。その後、次の agent がするとおりに verify skill を一度たどり、手順がまだ動くことを確かめる。

## 報告

チェックごとに、ユーザーに次を伝える。

- 結果と、読んだ commit。
- 検証の何をなぜ変えたか。変更ごとに短い理由を添える。コードの形が変わったのか、約束を意図して変えたのか（証拠つき）。
- 再実行の結果と、更新したチェックがまだ失敗できることを示すのに使った壊し方。
- 各バグを平易な言葉で。コードの言葉の手順としての反例、害、それを持ち込んだ commit。
- 検証がまだ覆っていないもの。覆うべきなのに覆っていない新しいコードも含める。

どの失敗が検証のずれで、どれがコードのバグかをはっきり言う。更新前に通り、更新後に失敗するチェックについては、古い pass が古い記述の上のものだったと言う。

検証の更新は、プロダクトの修正とは別の変更にまとめる。
