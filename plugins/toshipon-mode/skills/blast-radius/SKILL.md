# Blast radius

変更が出荷される前に、他の場所で何を壊すかを見つける。「blast radius of X」「what could this break」の質問や、まだ信用しきれない小さな diff のレビューに使う。

`how` と `why` の相棒である。`how` はそのコードが何をするかを教える。`why` はなぜその形になっているかを教える。Blast radius は、それが他の場所で何を壊すかを教える。

呼び出し元を列挙することが仕事ではない。それは agent が一瞬で grep できる。仕事は、grep では見えない破損を見つけることである。

## Don't trust your own writeup

もっともらしく聞こえる blast-radius の書きものには価値がない。それが真実かどうかにかかわらず説得力があるように読めてしまう。それこそが陥る罠である。だから書きものをそのまま渡さない。全体が依存している 1 つか 2 つの事実を見つけ、コードを実行して証明する。言葉は出発点であり、出荷するものではない。

### How sure are you

変更の安全性が依存している事実それぞれについて、コストが許す限り以下のリストのできるだけ下まで到達させ、どこで止まったかを明示する。

1. そう言った。それ自体には価値がない。
2. 該当行を指し示した。実際の `file:line`、あるいはライブラリ自身のソースコード。
3. 悪いケースが起こり得ないことを示した。失敗の経路をステップごとにたどり、そこに到達しないことを確認した。
4. 実際に実行した。実コードを呼び出し、間違っていれば大きな音を立てて失敗するスクリプトかテスト。
5. 実際に動いているアプリで再現させた。

ステップ 4 は、たいていアプリが出荷するのと同じライブラリを import し、懸念している関数そのものを呼び出す小さなスクリプト 1 本で足りる。

## Steps

1. 変更を読む。diff、それが追加・変更・削除するシンボル、そしてそれが今どう振る舞いを変えるか。diff に書かれていない部分も含めて読む。`why` のステップ 2 を使って PR とコミットを取得する。
2. それが安全である根拠となる 1 つの事実を見つける。怖く見える変更のほとんどは、「この呼び出しはすでに死んでいるキャッシュエントリしか削除せず、他には何もしない」といった、たった 1 つの事実によって安全になっている。その事実を見つける。それが成り立てば、怖く見えるケースの大半は一気に消える。長い「もしかしたら」のリストではなく、ここに時間を使う。
3. grep が止まる場所を見る。呼び出しているライブラリのソースを読み、固定されたバージョンとローカルパッチを確認する。何がいつ動くかを把握する。マイクロタスク、unmount とteardown、Solid か React か。シンボル検索が見逃すものを追う。API が返す JSON、DB のカラム、ワイヤーフォーマット、同じバイト列を読む別の言語、フィーチャーフラグ、3 ホップ下流のコード。
4. 各リスクについて正直に評価する。それが実際に起こる確率と、起きた場合の実際のコストを与える。確認したリスクだけを残し、確認して問題ないと分かったものは別に列挙する。`why` と同じルールに従う。実在する `file:line` を引用し、何も見つからなかった検索もそれ自体が答えであり、呼び出し元や API をでっち上げない。
5. その 1 つの事実を証明する。実コードを実行するスクリプトかテストを書き、実行し、実際に起きた結果を貼る。
6. 大きい、あるいは範囲の広い変更では `arena` として実行する。複数のモデルに同じ問いを尋ね、答えを統合する。モデルが違えば、拾える実バグも違う。

## What to hand back

- **What it does。** 何が変わったか。明白ではない部分も含める。
- **The one fact it's safe because of。** それを述べ、どのステップまで到達させたかを言い、証拠を示す。証明できなかった場合は unproven と書く。
- **Risks。** それぞれについて、どう壊れるか、`file:line`、確率とひどさ、確認方法を名指しする。重要なものには証拠を貼る。
- **Cleared。** 何を確認し、なぜ問題ないのかを書く。
- **Before you merge。** 実バグを捕まえる最も安価なテストや再現手順。自分が書いたスクリプトを含める。

`unslop` を通して書き、実在するコードを引用し、公開する前に非公開情報を取り除く。

**Reply:** 上記の書きもの。1 つの安全性の事実は、証明されているか unproven と明記されているかのどちらか。
