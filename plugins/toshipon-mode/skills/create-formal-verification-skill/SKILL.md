# Create a formal verification skill

テストは、誰かが書こうと思いついたケースを確かめる。形式検証は、明示した範囲のすべてのケースを確かめる。モデル内のあらゆる手順の順序、ある上限までのあらゆる入力、あるいはあらゆる入力である。この skill は、それが最も効く箇所をリポジトリから見つけ、その性質を 1 つ検証し、次の agent が変更をその性質に照らして確かめられる project-local skill を残す。その skill は、作業の途中で初めて読み、こちらの作業を一度も見ていない agent に向けて書く。ユーザーは検証言語を学ばなくても、結果を信頼して行動に移せなければならない。

## 対象はコードから選ぶ

コードベースから答え、観測できないことだけをユーザーに聞く。ユーザーが領域やバグを名指ししたら、そこから始める。

良い対象とは、コードが守る約束のうち、破れるとユーザーが害を受け、それを破るケースにテストがめったに届かないものである。検証しやすいものではなく、リポジトリで最も強い対象を選ぶ。

## ツールは問いが決める

問いに最も安く答えるツールを選ぶ。model checker、証明支援系、SMT ベースの verifier、またはその他のツールである。出来事が悪い順序で起こり得るかという問いには、設計の小さなモデルに対する model checker が合うことが多く、言語を問わず TLA+ を既定にする。メモリ安全性、オーバーフロー、データ構造の不変条件のように、コードそのものがあらゆる入力で正しく振る舞うかという問いには、コード上で動く verifier が合うことが多い。その言語で動く verifier がなければそう言い、関数を手で写したモデルではなく、実際のコードを生成した入力でテストする。上限では足りず、どの大きさでも成り立たなければならない性質には証明が要ることがある。リポジトリの開発者がインストールして実行できるツールを優先し、なぜそれを選んだかをユーザーに伝える。

## 良い検証の条件

- **コードに忠実。** モデルや証明の各部分は、レビュアーが開けるコードを指す。検証が 1 つの不可分な手順として扱うものは、コードでも 1 つの不可分な手順である。名前はこのリポジトリのものを使う。
- **失敗できる。** 失敗するのを一度も見たことのないチェックは何も証明しない。各性質が、それが守るコードを壊した版（チェックを外す、手順を入れ替えるなど）で失敗することを示す。
- **発見は発見のまま。** 現在のコードが性質を破るなら、反例をコードの言葉で報告する。通るまで性質やモデルを弱めない。ユーザーが頼まない限りプロダクトコードは変えない。
- **範囲に正直。** 何を、どの上限と仮定のもとで検証し、何を外したかを言う。通ったことが覆うのはモデルか上限の範囲であって、システム全体ではない。
- **ツールなしで読める。** 性質と害をそれぞれ平易な 1 文で述べる。反例は、コードの言葉で書いた短い手順の列として語る。
- **再実行が安い。** コマンド 1 つ、再現できるツールのバージョン、次の agent が関係する変更のたびに使うくらい短い実行時間。
- **コードと歩調を合わせる。** 各チェックが覆うファイルと関数、そして検証がそれらを記述していると最後に確かめた commit を記録する。その commit 以降に覆われたコードが変わったら、次の agent は検証を見直す必要があると分かる。

## verify skill を生成する

領域を名指しし、いつ使うかを書いた frontmatter を持つ project-local skill（`.claude/skills/<name>/SKILL.md`）を書く。frontmatter がないと skill は登録されない。次の agent がその skill だけを読んで、変更が検証済みのコードに触れるかを判断し、チェックを実行し、本物のバグとモデル化の誤りを見分け、意図した変更のときに検証を更新できなければならない。カバー範囲の記録と同期 commit を skill に書き、検証が新しい commit のコードを記述していると確かめてからだけ同期 commit を進めるよう、次の agent に指示する。このリポジトリの実際のコマンド、パス、名詞を使い、プレースホルダを残さない。

## 渡す前に証明する

生成した skill を次の agent がするとおりに一度たどり、実際のコードで性質を壊す使い捨ての変更に対して実行する。それは壊れを捕まえなければならない。その後、使い捨ての変更を捨て、チェックが元の状態に戻ったことを確かめる。通るか、報告する発見でだけ失敗するかである。一度も実行していない verify skill は下書きである。skill が壊れを見逃すか、手順が動かないなら、使い捨ての変更ではなく skill か検証を直す。

## 引き渡す

何を検証したか、どのツールをなぜ使ったか、上限、チェックが見つけたことを平易な言葉で、実行方法、そして何を覆っていないかをユーザーに伝える。2 つ目の対象は、近いものを見つけたときだけ提案する。検証を再確認せずに入った変更のあと、検証をコードに合わせ直すには `/toshipon-mode:maintain-formal-verification-skill` を使うよう案内する。
