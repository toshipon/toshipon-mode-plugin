# Review Rubric

関連するレンズだけを通してレビューする。すべてのレンズがすべての変更に当てはまるわけではない。判断に委ねる。

## Correctness

コードは意図が示す通りのことを実際に行っているか?

- エッジケース: 空の入力、nil/undefined、境界値、並行アクセス
- エラーハンドリング: エラーはキャッチされ、伝播されているか、それとも黙って握りつぶされているか?
- off-by-one、型強制、整数オーバーフロー、文字列エンコーディング
- 状態管理: 競合状態、古いクロージャ、ダングリング参照
- ハッピーパスは動くか? サッドパス(異常系)は動くか?
- 冪等性: この操作が 2 回実行されたら、あるいは前回の実行が途中でクラッシュしていたら何が起きるか? 答えが「残された状態次第」なら、整合を取るステップが欠けている。
- 並行性: 複数のアクターが同じ可変状態(ファイル、ブランチ、共有データ)に触れうる場合、アクセスは構造的に(ロック、逐次フェーズ、排他所有)直列化されているか、それとも守られるとは限らない慣習によって直列化されているか?

潜在的なバグを見つけたら、実行パスをたどること。単に「これは nil になりうる」と指摘するだけでなく、nil になる呼び出しチェーンを示すこと。

## Root Causes vs. Symptoms

コードは実際の問題を修正しているのか、それとも症状を覆い隠しているだけなのか?

これに答えるには、変更されたファイルの外を見る必要があることが多い。周辺のコード(呼び出し元、呼び出し先、型定義、兄弟モジュール)を読み、変更が置かれているアーキテクチャを理解すること。利用可能なツール(Read、Grep、Glob)を使って調査する。呼び出しチェーンをたどる。型を読む。変更が適切な層に対応しているかを判断する前に、なぜそのコードが存在するのかを理解する。

- より深い不変条件違反を覆い隠すガード節
- 壊れた契約を隠すリトライロジック
- モデリングの誤りを黙らせる型キャスト
- 回避策を見たら問う: なぜこの回避策が必要なのか? 適切な修正はどんな形になるか?
- モジュール A での修正が、本来はモジュール B の契約の修正であるべき場合
- 構造の方が優れている場面での指示: 修正が「X をするな」というコメントや、誰かが覚えておかなければならない慣習であるなら、代わりに型制約、lint ルール、あるいは誤りを不可能にするランタイムチェックにできないか問う

## Structural Integrity

コードは、それが属するシステムにうまく収まっているか?

- 境界の規律: バリデーションはシステムの境界にあるか、それともビジネスロジックに散在しているか? データはシステムに入る箇所で一度だけ検証し、その後は内部で信頼する。
- 抽象のレベル: コードは高レベルのオーケストレーションと低レベルの詳細を混在させていないか?
- 結合: この変更は、将来の変更を難しくする依存関係を持ち込んでいないか?
- データモデルの適合: データ構造は実際のアクセスパターンと一致しているか? 正しい構造は下流のコードを自明にし、誤った構造はあらゆる場面で抵抗する。
- 後付け vs 統合: この変更は既存の設計に継ぎ足されたのか、それとも設計が最初からそれを見込んでいたかのように読めるか? もし最初からこの新しい要件が分かっていたら、コードはこの形になっていただろうか?
- レガシーな二重パス: この変更は古いパスを生かしたまま新しい API を導入していないか? 外部の利用者がいないなら、同じ波で呼び出し元を移行し古いパスを削除すること。恒久化する互換レイヤーを残さないこと。

抽象を欠くというだけの理由でシンプルなコードにペナルティを課さないこと。時期尚早な抽象化は重複よりも悪い。

## Verification

コードを読んだだけで、それが動くとわかるか?

- テストはあるか? 振る舞いをテストしているか、それとも実装の詳細をテストしているか?
- 回帰を捉えられるアサーション/不変条件はあるか?
- バグ修正であれば: そのバグに対するテストはあるか?
- 統合境界に触れる変更であれば: 経路全体がテストされているか?
- 代理ではなく実物を確認する: コードがファイルの mtime やキャッシュされた状態を介して生存確認をしているなら、実際の値を読んでいないという検証のギャップがある。
- 委譲された作業や非同期の作業について: コードは実際の出力成果物を検証しているか、それとも自己申告のサマリーを信用しているか?

## Complexity Budget

その複雑さは、コードが達成することに見合っているか?

- 正しさや明快さを失わずにシンプルにできるコード
- 呼び出し箇所が 1 つしかない抽象
- まだ存在しないケースのための設定やパラメータ化
- デッドコード、未使用のインポート、名残のパラメータ
- オーバーエンジニアリング: 現在呼び出し元のない「念のため」のコードパス
- もはや必要ない移行期の安定性のために生かされたままの陳腐化した互換パス。移行が済んでいるなら、足場は削除する
- ユーザー体験はその複雑さに見合っているか? すべての機能、コントロール、オプションはその存在価値を証明すべきである。中途半端な機能は、存在しないよりも悪い。

シンプルな方が良い。ただしシンプルさが誤りである場合を除く。3 行の重複は、時期尚早な抽象化に勝る。

## Security

セキュリティ上の各所見について、入力の経路をコードを通じてたどり、それを示すこと。

- サニタイズなしに危険なシンク(SQL、シェル、eval、innerHTML)へ流れるユーザー入力
- 新しいエンドポイントにおける認証/認可のギャップ
- コード、ログ、エラーメッセージ内のシークレット
- セキュリティ上重要なパスにおける TOCTOU(time-of-check-time-of-use)
