# Lead Judgment Framework

## Filtering Principles

### Nitpick Gravity(揚げ足取りの重力)

レビュアー、特に敵対的なレビュアーは、レビューを埋め尽くそうとする傾向がある。重大な問題が見つからなければ、空白を埋めるために些末な指摘を水増しする。あるレビュアーの所見がすべて些末な指摘とスタイルの好みなら、そのコードはおそらく問題ない。そう述べること。

### Hypothetical vs. Actual(仮定 vs 実際)

「ここで誰かが null を渡したらどうなる?」は、呼び出し元が実際に null を渡せる場合にのみ所見となる。呼び出し箇所をたどること。入力が上流でバリデーションされているか、型システムが防いでいるなら、その所見は却下する。diff だけを見ているレビュアーは呼び出しチェーン全体を常に見られるわけではないが、あなたには見える。

### Premature Abstraction Warnings(時期尚早な抽象化への警告)

レビュアーはしばしば関数の抽出、インターフェースの追加、抽象の作成を提案する。このコードは 2 通り目の変化の仕方をする必要があるか? そうでないなら、その抽象は時期尚早である。動作するシンプルなインラインコードは、現在のスコープには過剰なクリーンな抽象に勝る。

### "I Would Have Done It Differently"(自分なら違うやり方をする)

これはコードレビューで最もよくある誤検出である。「私は別のアプローチの方が好み」に帰着する所見は、レビュアーが現行アプローチの具体的な問題を示さない限り、バグでも設計上の欠陥でも行動可能な指摘でもない。これらは却下し、理由を述べる。

### Missing Context Signals(文脈の欠落を示すシグナル)

レビュアーが文脈を理解していないことを示す所見に注意する:
- 著者が書いていない、あるいは変更していないコードへの変更を提案している
- コードベースの他の部分と整合するパターンを指摘している(レビュアーが単にそれを知らないだけ)
- あなたが知っている制約と矛盾するアプローチを推奨している

これらはレビュアーが限られた情報の中で犯した正直な誤りである。穏当に却下すること。

## When Reviewers Are Right

不快だからという理由だけで所見を却下しないこと。敵対的レビューの目的は、あなたが見落とすものを捕らえることにある。注目に値する所見のサイン:

- 複数のモデルが独立に同じ問題を指摘している(コンセンサスのシグナル)
- 所見が仮定ではなく具体的な実行パスを特定している
- 所見がコードに対するあなたのメンタルモデルのギャップを明らかにしている
- その所見を読んで「……いや、実際そうだ」と思う

セキュリティ上の所見と正しさに関するバグを却下する際は特に注意すること。単独のモデルからの指摘であっても、より慎重な精査に値する。
