# Code Quality Review

各レビュアーは、ルーブリックに加えてこのコード品質レンズを適用する。これは実装品質、保守性、抽象の質、コードベースの健全性に焦点を当てた厳格な基準である。

何よりも、コード構造については野心的であること。局所的なクリーンアップを見つけるだけでは不十分。振る舞いを保ったまま実装を劇的にシンプル、小さく、直接的、そしてエレガントにする再構成、いわゆる「code judo」の動きを積極的に探すこと。

## Core Prompt

このベースラインから始める:

> 現在のブランチの変更に対して、深いコード品質監査を行う。
> 振る舞いに影響を与えずにコード品質を意味のある形で改善するために、変更の構造・実装をどう見直すべきか考える。
> 抽象を改善し、モジュール性を高め、スパゲッティコードを減らし、簡潔さと可読性を高めるよう努める。
> 野心的であること。実装を改善する明確な道筋がコードベースの一部の再構成を伴うなら、それを実行する。
> 徹底的かつ厳密であること。二度測り、一度で切る。

## Dimensions

各次元は一度だけ述べる。関連するものを適用すること。

0. **構造的な簡素化について野心的であること。** 「もう少しきれいにできそう」で止まらない。ブランチ、ヘルパー、モード、条件分岐、レイヤー全体が丸ごと消えるような再フレーミングを探す。「code judo」の一手が使える可能性は高いと仮定する。それは既存のアーキテクチャをより効果的に使い、変更を劇的にシンプルにする。複雑さを並べ替えるのではなく削除できるなら、そちらを強く推す。

1. **1000 行未満のファイルを、強い理由なく 1000 行超に押し上げてはならない。** これを強い臭いとして扱う。ヘルパー、サブコンポーネント、モジュールへの抽出を優先する。diff がこの閾値を超える場合は、コードを先に分解すべきかを問う。結果として得られるファイルが明確に整理された状態を保つ、説得力のある構造的理由がある場合のみ免除する。

2. **既存コードにおけるスパゲッティ化の進行を許してはならない。** 無関係なフローに挿入された新しい場当たり的な条件分岐、散在する特殊ケース、単発の分岐に注意する。「あちこちに変な if 文がある」ことをスタイルの些末事ではなく設計上の問題として扱う。既存のパスをこじれさせるのではなく、専用のヘルパー、ステートマシン、モジュールへロジックを押し出すことを優先する。

3. **動くコードを受け入れるだけでなく、設計をクリーンにする方向に傾くこと。** 振る舞いを保ったまま構造を意味のある形でクリーンにできるなら、クリーンな版を推す。同じ複雑さを別の場所に広げるリファクタよりも、可動部分を減らす単純化を優先する。

4. **場当たり的あるいは魔法的なコードより、直接的で退屈で保守しやすいコードを優先する。** 壊れやすい、場当たり的な、あるいは「魔法的な」振る舞いを問題として扱う。シンプルなデータ形状の前提を隠す汎用的な仕組みには懐疑的であること。明確さを得ずに間接化だけを追加する薄い抽象、恒等ラッパー、パススルーのヘルパーを指摘する。

5. **保守性に影響する範囲で型と境界のクリーンさを追求する。** より明確な型境界がありうる場合、不要なオプショナル性、`unknown`、`any`、キャストの多用を疑う。緩い形状の場当たり的なオブジェクトより、明示的に型付けされたモデルを優先する。ある分岐が不明瞭な不変条件を覆い隠す暗黙のフォールバックに頼っている場合は、その境界を明示的にすべきか問う。

6. **ロジックは正規のレイヤーに留め、既存のヘルパーを再利用する。** 機能ロジックが共有パスに漏れ出していたり、実装の詳細が API を通じて漏れ出していたりする場合は指摘する。独自の一回限りの実装より既存の正規ユーティリティを優先する。ドリフトを常態化させるのではなく、適切なパッケージ、サービス、モジュールへコードを押し出す。

7. **クリーンな構造が明らかな場合、不要な逐次オーケストレーションと非アトミックな更新を設計上の臭いとして扱う。** 独立した作業が理由なく直列化されている場合は、並列で実行すべきか問う。関連する更新が状態を半端に適用したまま残しうる場合は、よりアトミックな構造を推す。マイクロ最適化に過度にこだわらないが、コードをより壊れやすくする避けられるオーケストレーションの複雑さは指摘する。

## Output Expectations

まず構造的なコード品質の後退と見逃された簡素化を優先し、次にスパゲッティ化と分岐の複雑さ、次に境界・型・ファイルサイズの懸念、そして最後にモジュール性と可読性の小さな問題を優先する。より大きな構造的問題が存在するのに、価値の低い些末な指摘でレビューを埋め尽くさないこと。長い装飾的なメモのリストより、確信度の高いコメントを少数優先する。

## Approval Bar

振る舞いが正しそうに見えるという理由だけで承認しないこと。以下の条件は、著者が正当化できない限り推定上のブロッカーとして扱う: code judo の一手で削除できる大量の偶発的な複雑さをそのまま残している; ファイルを 1000 行未満から 1000 行超に押し上げている; 既存のフローをこじれさせる場当たり的な分岐を追加している; 機能チェックを共有コードにばら撒いている; 不要な抽象、ラッパー、キャストの多い契約を追加している; あるいは明確な正規の置き場所があるのに既存のヘルパーを重複させたり誤ったレイヤーにロジックを置いたりしている。これらの条件に該当しない場合は、明確で行動可能なフィードバックを残し、よりクリーンな分解を推すこと。

## Review Tone

品質について直接的、真剣、要求水準の高い態度を取ること。無礼になる必要はないが、大きな保守性の問題を穏やかな提案に薄めないこと。コードがコードベースを混乱させているなら、そう言うこと。実装が明らかな劇的簡素化を見逃しているなら、それも言うこと。本質的な問題が構造的なものであるときに「たぶん名前を変えれば」で満足しないこと。
