# Interrogate

設定された各モデルにつきレビュアーを 1 人起動し、コード変更を敵対的にレビューさせる。敵対的なシグナルは、割り当てられたペルソナからではなく、モデルの多様性から生まれる。成果物は統合された判定である。変更を自動適用してはならない。

## Step 1, スコープ

文脈からレビュー対象を特定する:

- ユーザーが特定のファイルや diff を指している場合はそれを使う。
- feature ブランチ上であれば `git diff main...HEAD`(または適切なベースブランチ)を実行し、変更セット全体を取得する。
- ユーザーのメッセージが直近の作業を参照している場合は、関連ファイルを集める。

diff またはファイル内容を、レビュアーがコードを理解するために必要な周辺の文脈ファイルと一緒にまとめる。

## Step 2, 意図

レビュアーを起動する前に、ユーザーのメッセージ、コミットメッセージ、PR の説明(あれば)、コード自体から、意図を 1 つの明確な段落として述べる。意図に確信が持てない場合は、進める前にユーザーに確認する。

## Step 3, レビュアーを起動する

Agent tool で、下表のティアごとに 1 人ずつのレビュアーを 1 つのメッセージで起動する。

| Subagent | Model |
|----------|-------|
| Reviewer A | `opus` |
| Reviewer B | `sonnet` |
| Reviewer C | `haiku` |

各レビュアーは `subagent_type: "Explore"` とし、`model` に上表のティアを指定する。設定値が `inherit-parent` または `auto` の場合は `model` を省略し、親のモデルで走らせる。モデルが拒否された場合は、エラーメッセージ内の有効な値から最も近いもの(同じティアを優先)で起動し、その旨を述べる。モデル指定の問題でレビューをブロックしないこと。`inherit-parent` や `auto` を拒否された値として扱わないこと。

`references/reviewer-prompt.md` を読み、Step 2 の意図、diff またはファイル内容、`references/rubric.md` のルーブリック、`references/code-quality-review.md` のコード品質レンズで、すべてのレビュアーに同じテンプレートを埋めて渡す。各レビュアーの `effort` は toshipon-mode skill の Delegation 節に従って仕事に合わせて選ぶ。動かすのは `effort` だけでティアは変えない。変えるとパネルの多様性が失われる。

## Step 4, 統合する

結果が返ってくるにつれて、統一像を組み立てる。すべてのレビュアーの所見をパースする。同じ問題を異なる表現で記述した所見はマージし、どのモデルが指摘したかをメモする。2 つ以上のモデルが独立に指摘した所見が最もシグナルが高い。単独モデルの所見も読むが、それに応じて重みづける。不一致をメモする。あるモデルが何かを指摘し、別のモデルが明示的に反対のことを述べている場合、それは判定の文脈になる。

## Step 5, リードとしての判断

あなたはリードレビュアー、実務的なシニアエンジニアであり、中立的な集約者ではない。`references/lead-judgment.md` を読み、フレームワーク全体を把握する。すべての所見を次の 4 つのバケットのいずれかに入れ、指摘したモデルと一行の根拠を添える。

- **Act on**(対応する)。実際の目標に照らして、正しさ・セキュリティ・保守性に影響する実在の問題。実際の PR ならブロックされるレベル。
- **Consider**(検討する)。正当な指摘だが、今対応するコストに見合うか確信が持てない。ユーザーの注意を引く価値がある。
- **Noted**(記録する)。技術的には妥当だがアクションには繋がらない。文脈依存、時期尚早な最適化、現段階では影響が小さい。
- **Dismissed**(却下)。誤り、揚げ足取り、文脈の欠落。簡単な理由を添える。

## Output Format

### Intent
> [Step 2 で述べた意図の段落]

### Reviewers
- Reviewer [label]: [モデル名]、[N 件の所見](レビュアーごとに 1 箇条書き)

### Act On
[それぞれ: 説明、どのモデルが指摘したか、なぜ重要か。]

### Consider
[それぞれ: 説明、どのモデルが指摘したか、トレードオフ。]

### Noted
[簡潔なリスト。]

### Dismissed
[それぞれ簡単な理由を添える。]

### Agreement Map
[モデル間でどこが一致し、どこが分岐したか。そのパターンから何が読み取れるか。]
