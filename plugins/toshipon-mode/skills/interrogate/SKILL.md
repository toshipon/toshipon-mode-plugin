# Interrogate

設定された各モデルにつきレビュアーを 1 人起動し、コード変更を敵対的にレビューさせる。すべてのモデルに同じプロンプトとルーブリックを渡す。敵対的なシグナルは、割り当てられたペルソナからではなく、モデルの多様性から生まれる。モデルは盲点、事前分布、推論パターンが異なる。複数モデル間の一致は高信頼度のシグナルであり、単独モデルの所見も読む価値はあるが信頼度は低くなる。

成果物は統合された判定である。変更を自動適用してはならない。

## Step 1, スコープを決定する

文脈からレビュー対象を特定する:

- ユーザーが特定のファイルや diff を指している場合はそれを使う
- feature ブランチ上であれば `git diff main...HEAD`(または適切なベースブランチ)を実行し、変更セット全体を取得する
- ユーザーのメッセージが直近の作業を参照している場合は、関連ファイルを集める

diff(またはファイル内容)と、レビュアーがコードを理解するために必要な周辺の文脈ファイルをまとめる。

## Step 2, 意図を述べる

レビュアーを起動する前に、意図を明示的に述べる。このコードは何を達成しようとしているのか? 以下から導出する:

- ユーザーのメッセージ
- コミットメッセージ
- PR の説明(あれば)
- コード自体

1 つの明確な段落として書く。レビュアーは、意図そのものが正しいかではなく、その作業が意図をうまく達成しているかに異議を唱える。意図に確信が持てない場合は、進める前にユーザーに確認する。

## Step 3, レビュアーを起動する

Agent tool を使い、下表のティアごとに 1 人ずつのレビュアーを 1 つのメッセージで起動する。

| Subagent | Model |
|----------|-------|
| Reviewer A | `opus` |
| Reviewer B | `sonnet` |
| Reviewer C | `haiku` |

各レビュアーについて:
- Agent tool の `subagent_type`: `"Explore"`
- Agent tool の `model`: 上表のティア

サブエージェントを起動しようとしたときにモデル slug が解決不能として拒否された場合は、Agent tool のエラーメッセージ内で有効な slug を確認し、最も近い同等物(同じファミリー内で最も推論力の高いティアを優先)を選び、有効な slug で起動し、設定値やデフォルトテーブルを更新する別の PR を開く。slug の問題でレビューをブロックしないこと。設定値が `inherit-parent` または `auto` の場合は `model` を省略する。これらのエイリアスを壊れた slug として扱ったり、このフォールバックに入れたりしないこと。

`references/reviewer-prompt.md` を読み、テンプレートに以下を埋める:
1. Step 2 で述べた意図
2. diff またはファイル内容
3. `references/rubric.md` のレビュールーブリック
4. `references/code-quality-review.md` のコード品質レンズ

同じ埋め込み済みテンプレートをすべてのレビュアーに渡すので、すべてのモデルがコード品質レンズを適用することになる。

各レビュアーは、プロンプトテンプレートに記載された構造化された所見を出力する。

## Step 4, 統合する

結果が返ってくるにつれて、統一像を組み立てる:

1. レビュアーからの**すべての所見をパースする**
2. **コンセンサスを特定する**。2 つ以上のモデルが独立に指摘した所見が最もシグナルが高い。
3. **単独モデルの所見を特定する**。読む価値はあるが、それに応じて重みづける。
4. **重複を排除する**。モデルによって同じ問題を異なる表現で記述することがある。これらをマージし、どのモデルが指摘したかをメモする。
5. **不一致をメモする**。あるモデルが何かを指摘し、別のモデルが明示的に反対のことを述べている場合、それは判定に有用な文脈である。

## Step 5, リードとしての判断

あなたはリードレビュアー、実務的なシニアエンジニアであり、中立的な集約者ではない。

`references/lead-judgment.md` を読み、フレームワーク全体を把握する。レビュアーはコードベースの一部分しか見ていない。あなたは完全な文脈(目標、制約、タイムライン、すでに検討されたトレードオフ)を持っている。それを積極的に活用する。

すべての所見を以下のバケットで分類する:

- **Act on**(対応する)。実際の目標に照らして、正しさ・セキュリティ・保守性に影響する実在の問題。実際の PR ならブロックされるレベル。
- **Consider**(検討する)。正当な指摘だが、今すぐ対応するコストがそれに見合うか確信が持てない。ユーザーの注意を引く価値がある。
- **Noted**(記録する)。技術的には妥当だがアクションには繋がらない。文脈依存、時期尚早な最適化、現段階では影響が小さい。
- **Dismissed**(却下)。誤り、揚げ足取り、文脈の欠落。簡単な理由を添える。

各所見について、以下を含める:
- どのモデルが指摘したか
- カテゴリ(act on / consider / noted / dismissed)
- 分類の一行の根拠

## Output Format

この構造で判定を提示する:

### Intent
> [Step 2 で述べた意図の段落]

### Reviewers
- Reviewer [label]: [モデル名]、[N 件の所見](レビュアーごとに 1 箇条書き)

### Act On
[対応すべき所見。それぞれについて: 説明、どのモデルが指摘したか、なぜ重要か。]

### Consider
[検討する価値のある所見。それぞれについて: 説明、どのモデルが指摘したか、関わるトレードオフ。]

### Noted
[妥当だが優先度は低いもの。簡潔なリスト。]

### Dismissed
[却下した所見と簡単な理由。ユーザーが何がフィルタリングされたか、なぜかを確認できるようにし、異論があれば判断を上書きできるようにする。]

### Agreement Map
[モデル間でどこが一致し、どこが分岐したか。その一致・不一致のパターンから何が読み取れるか。]
