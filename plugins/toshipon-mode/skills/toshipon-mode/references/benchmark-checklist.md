# Benchmark checklist

性能の数値を出すときに使う。PR の before / after、regression の主張、繰り返し改善を回すための計測 harness、ライブラリや設定の選択などである。各質問には、コードについての推測ではなく、実行から得た証拠で答える。

ユーザーが求めたのがざっくりした目安なら、1 回の実行で足りる。それでも質問 4 と 7 は確認し、1 回の実行であることを明記する。その実行がおかしく見えない限り、残りは飛ばしてよい。選択肢の中から選ぶ判断は、決してざっくりした目安ではない。

## 何かを実行する前に

- 出すつもりの主張を、そのまま出す言葉で書き出す（「60k 行のデータセットで export が p50 で 30% 速い」）。質問はその文を検証するためのものである。
- 計測スクリプトを読む。何を計時し、何を数え、何を無視しているかを控える。
- `uptime` で load average を、`nproc`（macOS では `sysctl -n hw.ncpu`）で core 数を確認する。マシンが忙しければ、何が動いているかを突き止める。止められないなら、両側を交互に実行して同じノイズを受けるようにし、そのことを報告に書く。

## 質問

1. **なぜ 2 倍ではないのか。** limiter を名指しする。profile は報告しない実行で取る。profiler や tracer は作業を遅くするからである。プロセスごとの CPU（`top`、`pidstat`）、ランタイムの profiler（`node --cpu-prof`、`py-spy`、`perf`）、I/O wait、syscall 回数（Linux では `strace -c`）を使い、hot spot を source に対応付ける。load generator も見る。先に load generator が飽和したなら、測ったのは load generator である。変更が数値を動かさなかったなら、その理由は limiter が説明する。変更を無意味と断じる前に limiter を見つける。
2. **チューニングされていたか。** すべての側を本番と同じように動かす。release build、本番のフラグと環境変数、batching と transaction の設定、connection pool、本番と同じ程度に warm または cold なキャッシュ、同じバージョンとデータである。片側がデフォルトのままなら、比べたのは実装ではなく設定である。limiter が設定そのもの（1 行ごとの commit、debug build、欠けた index）なら、その側はチューニングされていない。チューニングしてから測り直し、その後に勝者を選ぶ。チューニングできないなら、その実行から勝者を選ばない。ユーザーが何を採用するかを選んでいる場合、主張を「今出荷されているコードでは」に狭めてもこの問題は解決しない。ユーザーが採用するのは選択肢そのものであって、今の設定ではないからである。
3. **限界を超えていないか。** 計算する。bytes/s を disk と network の帯域と比べ、ops/s × 1 操作あたりのコストを core 数と比べ、短縮された時間を変更した部分にかかっていた時間と比べる。実行時間の 10% を占める部分を取り除いても、実行はせいぜい約 11% しか速くならない。限界を超えた結果は、作業以外の何か、たとえばキャッシュ、no-op、バグを測っている。
4. **エラーは出ていないか。** 失敗と非成功レスポンスを数え、出力が存在するだけでなく正しいことを確認する。拒否はたいてい速く、timeout と retry は遅い。スクリプトがエラーを数えていないなら、数える処理を足す。
5. **再現するか。** 各側を少なくとも 5 回、交互に（A、B、A、B…）実行し、warmup、遅延初期化、キャッシュ、ドリフトがどちらかに有利に働かないようにする。中央値と範囲を報告する。実行ごとのばらつきより小さい差は、測定可能な差ではない。際どい場合は rank-sum 検定か、harness 自身の統計を使う。
6. **意味があるか。** micro な結果の隣に、ユーザーが実際に待つ end-to-end の経路を、現実的なデータサイズと並行度で測り、micro な結果を全体に占める割合として報告する。リクエストの 1% を占める helper は、どれだけ速くしてもリクエストをせいぜい 1% しか速くできない。
7. **そもそも作業は行われたか。** 計時した区間の中で作業が実行されたことを確認する。リクエストがサーバーに届いた、行が書き込まれた、bytes が読まれた、コードがその結果を使った、である。遅延評価のコード（誰もイテレートしない generator、誰も await しない promise、JIT が捨てられる結果）や timeout は、行われなかった作業についての数値を生む。

## 報告

- 結論を先に書く。速くなった、遅くなった、測定可能な差はない、判断不能、のいずれかである。
- 数値を単位、実行回数、範囲、limiter とともに示す。例:「p50 41 ms → 33 ms、各側 7 回の中央値、変更後の範囲 32〜35 ms、1 core 上の JSON parse で律速」。
- 差を主張しているのに limiter を名指しできないとき、片側がチューニングされていなかったとき、質問 4 と 7 を確認できなかったときは、判断不能とする。何が欠けているかを書く。
- PR 本文に載せる主な数値は 1 つに絞る。実行結果、範囲、limiter の証拠は、リンクした artifact かメモのファイルに置く。

## 他の性能関連の作業

- [Perf issue](../playbooks/perf-issue.md) playbook が baseline から計画を立てる前に、その baseline をこのチェックリストで検証し、以降のすべての数値も同様に検証する。
- 改善を繰り返し試すための計測 harness を固定するなら、固定する前にこのチェックリストで検証する。固定した harness がエラー数と作業量を出力するようにしておけば、各試行を採用するか戻すかの判断のたびに、質問 4 と 7 を追加のコストなしで確認できる。
