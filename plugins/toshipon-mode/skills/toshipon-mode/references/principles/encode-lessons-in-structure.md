# Encode Lessons in Structure

繰り返し発生する修正は、文章による指示ではなく、mechanism（tool、コード、メタデータ、automation）にエンコードする。すべてのエラー、人間による訂正、想定外の結果は学習シグナルである。それを捕捉し、適切な層へ振り分け、ループを閉じる。

**理由:** 文章による指示は見落とされやすい。読み手がそれに気づき、記憶し、遵守することを要求する。構造的な mechanism（lint rule、メタデータフラグ、ランタイムチェック、automation script）は協力がなくてもルールを強制できる。

**パターン:**
同じ指示を 2 回目書いていると気づいたら:
1. 問う: これは lint rule、メタデータフラグ、ランタイムチェック、script にできないか
2. できるなら、それをエンコードし、指示文は削除する
3. できないなら（本当に判断力を要する場合）、指示をより目立たせ、失敗パターンの具体例を添える

**最も強い手段を選ぶ。** 複数の mechanism が有効な場合は、状況が許す最も強いものを選ぶ（コンパイルできない表現不可能な状態 → CI を落とす lint や禁止 API → canonical な helper → ランタイムチェック、の順に強い）。agent は周囲のコードが既にやっていることをそのまま模倣するため、弱いガードは次のテンプレートになってしまう。

**系:** 症状を覆い隠さない。修正が構造的なものであれば、構造的な修正のみを用いる。指示文そのものが症状である。

**フィードバックループ:**
- **すべての訂正を捕捉する。** 人間が介入した、あるいはテストが失敗した時、それが一度限りかパターンかを判断する。
- **適切な層へ振り分ける。** 一度限り → メモに記録。繰り返す修正 → skill か lint rule。システム的な問題 → principle。
- **ループを閉じる。** 記録するだけで終わらせない。今すぐ適用するか、具体的な todo を作る。

**アンチパターン:**
- 記録せずに了承だけする（「覚えておきます」は永続しない）
- 振り分けずに記録だけする（本来あるべき lint rule についてのメモは、その lint rule が実装されない限り無駄になる）
- 一般化せずに修正だけする（1 件だけ直して、繰り返すパターンをそのまま残す）
