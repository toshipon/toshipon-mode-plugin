# Explain the Number

- **「なぜ 2 倍ではないのか」を問う。** 結果を頭打ちにしている resource か code path を名指しする。たとえば 1 つの core、lock、disk、network、あるいは load generator そのものである。それは実行中に取った profile かシステムカウンタから得て、source に対応付ける。コードを読んで推測したものは limiter ではない。数値がなぜ 2 倍良くならないのかを言えないなら、自分が何を測ったのか分かっていない。
- **その数値が他に何を測っている可能性があるかを列挙し、それぞれを証拠で潰す。** よくある候補は、エラー、スキップされた作業やキャッシュされた作業、実行されなかったコード、チューニングされていない側（デフォルト設定のまま放置された側）、ノイズ、そして end-to-end で効くには小さすぎる部分である。
- **証拠を数値と一緒に残す。** 実行回数、ばらつき、limiter をメモかリンクした artifact に書く。

性能の数値なら、[benchmark-checklist](../benchmark-checklist.md) の手順を全部通す。eval の結果なら、試行に同じことを問う。すべての実行がタスクをこなしたか、差は試行とモデルをまたいで保たれるか、そのシナリオに意味があるか。

数値の裏付けに実行回数・ばらつき・名指しされた limiter のどれかが欠けているとき、あるいは短縮された時間が、変更した部分にもともとかかっていた時間より大きいとき、この principle を飛ばしている。

[Prove It Works](prove-it-works.md) とは別物である。あちらは出力が本物であることを確かめる。
