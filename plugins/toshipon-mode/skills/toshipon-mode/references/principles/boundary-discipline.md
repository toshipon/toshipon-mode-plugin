# Boundary Discipline

バリデーション・型の絞り込み・エラーハンドリングはシステム境界に集中させる。内部コードは無条件に信頼する。ビジネスロジックは純粋関数として存在させ、シェルは薄く機械的にする。

**理由:** バリデーションが散らばると、ノイズが増え、冗長になり、誤った安全感を与える。データは境界で一度だけ検証する。ロジックをフレームワークの配線から切り離せば、フレームワークなしでテストできる。

**パターン:**
- **境界で**（CLI 引数、設定ファイル、外部 API、ネットワークプロトコル）: 検証し、エラーを返し、防御的に扱う。
- **システム内部では:** 型付きデータ、エラーの伝播、再検証はしない。型を信頼する。
- **境界を越えるとき。** 境界内部の私的な表現ではなく、ドメイン概念を公開する。汎用的な mechanism は内側に置き、特化した policy は edge に置く。

**適用例:**

バリデーションとエラーハンドリング:
- config はビジネスロジック内ではなく、パース時（境界）に検証する
- 生データは境界でドメイン型にパースする
- transport・storage・framework・wire の型を public surface に再エクスポートしない
- 境界で既に検証済みなら、呼び出し階層の奥で冗長な nil チェックを行わない

コード構成:
- ビジネスロジックは framework 依存のない純粋関数にする
- パース関数: 生バイトから型付き state への純粋な変換にする
- プロンプト構築: 構造化された state を入力にし、string を出力する
- スコアリングと評価: state から結果への純粋な変換にする

**テスト:**
- 「このデータは今まさにシステム境界を越えているか」。越えていないなら、そのバリデーションは冗長。
- 「これはシェルが呼ぶだけの純粋関数にできるか」。できるなら、抽出する。
