# Model the Domain

実際のドメインを条件分岐に散らばせるのではなく、データ構造にエンコードする。

**理由:** 散らばった boolean、繰り返される形状の前提、ファイル間に散らばる分岐は accidental complexity である。ドメインに合致した構造は無効な状態を表現不可能にし、分岐を削除する。書く時点でそれを選ぶのは安いが、後から回復しようとするとリファクタリング扱いになり先送りにされる。

**候補となる構造:**

- 散らばった boolean・フェーズ・lifecycle チェックの代わりに state machine。
- ゆるいパラメータや繰り返される形状の前提の代わりに型付きオブジェクト/モデル。
- ファイル間に散らばる分岐の代わりに map、registry、lookup table、discriminated union。
- 場当たり的な state mutation の代わりに reducer や command/event モデル。
- load・validate・transform・save のような手順の代わりに、1 つのドメイン知識のまとまりを中心に組織されたモジュール。実行順序は所有権ではない。
- 繰り返される振る舞い・所有権・不変条件を集約する小さなモジュール境界。
- データアクセスパターンがそれを求める場合の queue、cache、index、graph/tree、正規化されたコレクション。
- その他、状況に合う構造。上記のリストはよくあるケースを網羅しているにすぎない。どれも合わない場合は、コードが決して許してはならないことと、データがどう読まれるかを整理し、それをそのままエンコードする構造を見つける。

抽象化を無理に押し付けない。現在の形状が既に明確でローカルであり、成長しそうにないなら、素朴なコードを優先する。分岐・重複ルール・無効な状態・lifecycle リスクを取り除かずに間接参照だけを増やす抽象化には懐疑的であること。

これを見送ったサインは、既存の if/else チェーンにもう一つ分岐を足すだけの新機能や、最初の boolean と同期させ続けなければならない 2 つ目の boolean である。時間軸で分解すること（temporal decomposition）も別のサインである。フェーズ名を冠したモジュールは、各ステップで同じドメインルールを繰り返す。
