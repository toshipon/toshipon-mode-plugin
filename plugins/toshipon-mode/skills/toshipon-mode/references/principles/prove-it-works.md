# Prove It Works

すべてのタスクの出力は、実物を直接確認して検証する。proxy、自己申告、「コンパイルが通った」から推測しない。

**理由:** 検証されていない作業は正しさが不明である。間接的な検証（ファイルの mtime、出力の新しさ、agent の自己申告、キャッシュされたスクリーンショット）は直接観察より安く感じられる。しかし誤った推論に基づいて行動するコストは、情報源を確認するコストをはるかに上回る。

**パターン:** どんなタスクを完了させた後も、「これが実際に動くことをどう証明するか」を問う。

proxy ではなく実物を確認する:
- プロセスの生存は、派生した state を経由せず直接確認する
- キャッシュされた表現や派生した表現ではなく、実際の値を読む
- 検証に失敗したら、システムより先に観察方法自体を疑う

コードと機能:
1. ビルドする（必要だが十分ではない）
2. 実行し、実際の機能経路を動かす
3. 一連の流れを確認する。データは入力から出力まで正しく流れるか
4. 統合部分は、通信経路全体を end-to-end でテストする

委譲: 自己申告ではなく成果物を信頼する。
委譲した作業を検証する時は、委譲先の要約ではなく実際の出力成果物（git diff、ファイルの中身、ランタイムの挙動）を確認する。agent は自分が意図したことを報告するのであって、常に実際に起きたことを報告するとは限らない。

## 可能な限りチェックをスクリプト化する

最も強い証明は、一度きりの目視確認ではなく、同じ比較を再実行できる決定論的なスクリプトである。スクリプトを書き、実行し、その出力を、あなたの言葉を信じる代わりにレビュアーが再実行できる artifact として残す。旧・新のコンパイル結果を比較するスクリプトは、一目では見落とすものを捕まえる。

artifact は人間に見える状態にしておく。commit するのは、大規模な port や migration のように、後で監査可能な証跡が必要な大規模・複雑な作業だけに限る。ほとんどの作業は見える状態にしておくだけで十分で、commit までは不要である。
