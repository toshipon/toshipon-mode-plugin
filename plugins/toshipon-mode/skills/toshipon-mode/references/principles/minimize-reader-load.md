# Minimize Reader Load

保守性とは、読み手がコードを理解するために払わなければならない作業量である。次の 2 つの軸を追う。
1. **たどるべき層の数。** 問いと答えの間にいくつの間接参照があるか。
2. **保持すべき state の量。** 読み手が頭の中に保持しなければならない隠れた state・可変な context がどれだけあるか。

**理由:** コードは書かれる以上に読まれる。LOC、循環的複雑度、「クリーンアーキテクチャ」はあくまで proxy にすぎない。重要なのは reader load そのものである。この 2 つの軸は独立している。50 個のグローバル変数を持つ平坦な 1 ファイルは、6 層の adapter スタックと同じくらい理解しづらくなりうる。両方をガードする。これは [Guard the Context Window](guard-the-context-window.md) の人間版に当たる。working memory は読み手にとっても有限である。

**パターン:**
- **見合わない層は畳む。** 呼び出し元が 1 つしかない wrapper、2 つ目の実装がない adapter、来なかった未来のために導入された間接参照。これらはインライン化する。
- **隣接する層は抽象度を変えさせる。** 同じメソッドと引数を繰り返すだけの層は、圧縮を伴わずに reader load を増やす。pass-through な層は畳む。
- **インターフェースの圧縮を要求する。** ほとんど複雑さを隠さない広いインターフェースは、読み手に surface と実装の両方を学ばせることになる。意味のある判断を隠す境界を優先する。
- **state のスコープを縮める:** 純粋関数（mutation より return）、フィールドよりローカル変数、モジュール state よりフィールド、グローバルよりモジュール state を優先する。同期させるのではなく、導出する。
- **不変条件は境界で一度だけ名付ける。** 各利用箇所ごとにではなく境界で名付けることで、読み手は一度学べば済む。
- 層や state を追加する前に、それがどこか他の場所の reader load を同等以上に減らすかを問う。

**テスト:** 新しい読み手が「X はどこから来るのか」「何が X を変更できるのか」に 30 秒以内で答えられるか。答えられないなら、層か state を削る。
