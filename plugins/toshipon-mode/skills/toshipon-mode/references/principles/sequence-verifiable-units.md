# Sequence work into verifiable units

作業を、それぞれ確認可能な状態で終わる小さな単位の連なりとして順序付け、現在の単位が green になるまで次に進まない。同じ規律が、実行の仕方と提出の仕方という 2 つの高度で同時に効いてくる。

**理由:** 破壊を引き起こした単位そのもので検知できれば、局所化のコストは低い。バッチの後にまとめて検知すると、その破壊は埋もれてしまい、しかも既に壊れた土台の上にさらに積み上げてしまっている。同じ単位をレビュアーが再生できる提出物として順序付ければ、「信じてください」が「red になり、そして green になるのを見てください」に変わる。

**実行。** スイープ、migration、あるいは類似の編集を連続で行う際は、次の変更に取り掛かる前に各変更を検証する。編集をまとめて最後に一度だけ検証することは決してしない。各単位は before/after のブラケットである。既知の良好な状態、1 つの変更、チェックの実行、そして次へ進む。まずクリーンな trunk に rebase しておくことで、すべてのチェックが本物のベースラインに対して測定される。lever が編集を行う場合、単位ごとのチェックはほぼ無料になるが、それでも実行する。

**提出。** commit と PR は、作業を証明する順序で積み上げる。定番の形は、まず失敗するテスト、その上に修正を乗せる形である。最初の単位はバグが実在することを示し（red）、次の単位はそれが解消されたことを示す（green）。これによりレビュアーは問題とその証明の両方を見られる。他のストーリー順序としては、reshape の前の subtraction、treatment の前の baseline capture、feature の前の scaffold などがある。それぞれの commit はそれ単体で成立し、その連なりが一つの論証として読める。

**パターン:**
- チェックで終わる最小の単位を選ぶ。編集とそのテストのペア、あるいは単体で成立する commit。
- 次に進む前に検証する。単位ごとに red から green へ、最終バッチへの先送りは行わない。
- 単位の並び順自体が確信を積み上げるようにする。実行中の自分にとっても、スタックを読むレビュアーにとっても。

各チェックを本物に保つ [Prove It Works](prove-it-works.md) principle と、単位ごとのチェックを安価にする「build-the-lever」principle（本セットには含まれない）を、順序付けの面で補完するものである。
