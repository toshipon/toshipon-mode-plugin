# Fix Root Causes

デバッグ時は、症状が表に出た場所ではなく、故障そのものを直す。症状とは、誤った state が目に見えるようになった場所である。根本原因とは、システムがすべきでないことを最初にした場所、または扱うべき state を扱えなかった最初の場所である。

**理由:** 症状への対処は証拠を隠し、故障を別の場所で再び表に出るまま放置する。対処を重ねるたびにシステムは推論しづらくなる。誰も名前を付けていないバグのためのワークアラウンドを、コードが抱え込むことになるからである。

**パターン:**
- まず再現させる（再現できなければ、修正を検証できない）。
- 各段階で「なぜ」を問い、答えが前の段階の帰結ではなく、コードの中の誤った判断そのものになるまで続ける。
- 行き詰まったら計測する。実際のエラーと実際の state を読む。推測しない。
- 症状を引き起こした state が正当なものかを問う。システムがその state になりうるなら、そこで壊れたコードが根本原因であり、その場でその state を扱うことが修正である。その state が本来存在してはならないなら、壊れた場所にチェックを足すとバグが隠れる。その state を生み出したものを探す。ガード、retry、握りつぶしたエラー、clamp した値、捨てた state は、バグを隠すよくある手口である。
- 再起動後にだけ失敗するなら、まず永続化された state（config ファイル、キャッシュ、ロックファイル、シリアライズされた state）を疑う。実行間でコードは変わらず、変わるのは state だからである。
- 個別の事例だけでなくパターンを確認する。同じ故障を持つ箇所をすべて見つけ、すべて直す。
- ワークアラウンドを正当化するのに段落レベルのコメントが要るなら、コードが間違っている。コメントではなくコードを直す。
- 決め手となった事実を見つけるのに深い掘り下げが必要だったなら、最初の一目でそれを示せたはずの、安価で常時動くシグナルを提案する。
