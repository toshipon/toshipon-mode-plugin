# Laziness Protocol

コードを書くこと自体はあなたにとって安く、それが over-engineering を招きやすくする。人間の maintainer が抱く疲労感を借りて、それに対抗する。最小のコードと複雑さで最大の結果を狙う。

- **削除を優先する。** リファクタリングや改善を求められたら、追加より先に削除できるものを探す。
- **呼び出し階層を平らに保つ。** 深い呼び出しチェーンを避ける。相当な作業を隠す豊かなインターフェースは深い呼び出しチェーンには当たらない。ある問いに答えるのに 3 つ以上のファイルや層をたどる必要があるなら、それを平坦化する。
- **判断を一箇所に集約する。** 同じ選択を複数箇所で繰り返さない。単一の source of truth の背後に置き、結果を単純なフラグとして渡す。
- **diff を最小化する。** 問題を解決する最小の変更にする。「エレガント」な boilerplate より少ない行数を優先する。
- **配線そのものを疑う。** タスクが新しいシグナルを型・スキーマ・パイプライン等の層に通すよう求めてきたら、立ち止まってもっと直接的な経路を探す。
- **小さな漏れを見逃さない。** 小さな pass-through、表現の漏れ、重複した判断は広がる前に取り除く。小さな漏れは積み重なって恒久的な調整コストになる。

**最優先方針:** 人間の開発者がそのコードを保守するのに疲弊するようであれば、それは悪い解決策である。怠惰であれ。シンプルであり続けろ。
