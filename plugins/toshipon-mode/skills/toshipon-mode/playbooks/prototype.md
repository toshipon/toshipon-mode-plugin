### Prototype

**設計判断はあなたが持つものであり、コードではない。prototype は使い捨ての道具であり、実際のビルドは Feature に従う。** 「prototype」「mock it up」「sketch this」「try this layout」向け、あるいは commit する前に UI・インタラクション・レイアウトを探る場合。あるいは、それがなければ人間に聞いてしまう質問を、素早いスケッチで答えられるときに、経験的な分岐（どの挙動、どのタイミング、どのアプローチ）を決着させる場合にも使う。

Laziness Protocol の「最小の変更」と検証バーが逆転する唯一の playbook。速さが磨き上げより優先され、コード品質は問題にならず、計画も不要。規律は正しい設計を安く選ぶことに宿る。大胆であれ。ユーザーが頼んでいないバリエーションを提案し、あるアプローチを捨てて別のものを試す。

1. prototype が存在する目的である判断をスコープする。どのレイアウトか、どのインタラクションか、どの密度か、あるいは経験的な分岐ならどの挙動、タイミング、アプローチか。判断がなければ prototype もない。Feature にルーティングする。
2. 設計空間が開いている場合は参考資料を集める。先行事例を探し、テーマ・パレット・レイアウトの moodboard をまとめ、構築前にユーザーに方向性を選ばせる。方向性が決まっている場合はスキップする。
3. production の source とは別の、独立した scratch dir で使い捨てを構築する。リポジトリではなく session scratchpad ディレクトリを使う。視覚的な判断には、vanilla の HTML/CSS/JS か、アイデアを描画できる最も軽いスタック、CDN の依存関係、hot reload 付きの dev server。挙動やタイミングの判断には、問いを試せる最小の script。production framework、テスト、抽象化は不要。
4. 代替案を比較する場合は、1 つの切り替え器（ボタンかキー入力）の背後に 2、3 個の競合するバリアントを構築し、ユーザーが名前を付けられるようそれぞれにラベルを付ける。設計空間を安く使い尽くすことが目的であり、バリアントが 1 つでは比較にならない。
5. 一致する surface で検証する。視覚的な判断には、driver skill 経由で各バリアントをスクリーンショットし、インタラクションを駆動する。目がテストである。挙動やタイミングの判断には、タイミングを log したり、出力を print したり、レンダリングを見たりして、決めようとしていることそのものを観測する。ここではその観測がテストであり、assertion ではない。
6. 代替案、トレードオフ、推奨を提示する。出力は判断と使い捨ての成果物であり、出荷可能なコードではない。選ばれた方向性は、実際のビルドのために **Feature**（あるいは形状のために `architect` agent）に渡す。

**Reply:** 探ったバリアント、証拠（視覚的判断ならスクリーンショット、挙動的判断なら観測された出力やタイミング）、トレードオフ、あなたの推奨、scratch のパス。prototype が使い捨てであることをはっきり述べる。
