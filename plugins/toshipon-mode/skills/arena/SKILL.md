# Arena

何かを起動する前に、フェーズごとに 1 項目(Frame、Fan out、Cross-judge、Pick、Graft、Verify)の todolist を開く。

## Phase A: Frame

すべての候補が同じプロンプトを受け取るので、プロンプトが契約である。

1. 各候補が生成する成果物を明記する。
2. ルーブリックを導出する。*このタスク*における成功を、3〜6 個の具体的で採点可能な基準にする。具体的: `--dry-run フラグを追加し、書き込みをスキップする`。曖昧: `コードが正しい`。ルーブリックは Phase D で picker が使う道具であり、候補にはタスクしか見せない。
3. runner を選ぶ。既定は Agent tool の `model` オプションで `opus`、`sonnet`、`haiku` に 1 つずつ。arena が複数の設計方針をカバーする場合はさらに多く起動する。ジャッジよりも生成量が問われる作業では、同じモデルを N 回起動する。各サブエージェントの `effort` は toshipon-mode skill の Delegation 節に従って仕事に合わせて選ぶ。
4. 各候補に専用の出力先(可能なら git worktree、それが無理なら `/tmp/arena-<slug>/candidate-<n>/`)を与える。N 個の候補が同じパスに書き込むのは共有可変状態であり、何かを直列化する前に出力先を分離する。

## Phase B: Fan out

Agent tool で `subagent_type: "general-purpose"`、`run_in_background: true` を指定し、N 個のサブエージェントすべてを 1 つのメッセージで起動する。各サブエージェントには、タスク、共有グラウンディングへのパス、自分専用の出力先を渡し、成果物と、検討した代替案と却下したものを明記した短い根拠を作るよう指示する。

候補が成果物を生成しなかった場合は、N-1 で続行し、その離脱を記録する。

## Phase C: Cross-judge

Phase B のすべての候補が完了したら、`opus`、`sonnet`、`haiku` の中からジャッジのティアを選ぶ。ほとんどの runner が使ったティアとは異なるティアを優先する。Agent tool でそのモデルの Explore サブエージェント(`subagent_type: "Explore"`)を 1 つ起動する。ジャッジはルーブリックとパスラベル付きの候補を見て、基準ごとに採点し、根拠付きでベースを推薦する。これは Phase D のあなた自身の読み込みと並行して走る。候補がまだ書き込み中には起動しない。

## Phase D: Pick a base

ベースを選ぶ前に、すべての候補を最初から最後まで読む。全体的な印象ではなくルーブリックの基準ごとに各候補を採点し、cross-judge と比較する。ベースについての一致は選択の裏付けになる。不一致は、あなたか cross-judge のどちらかにバイアスがあるか、ルーブリックが曖昧だったことを意味する。決める前に両方の根拠を読む。

将来のメンテナが不変条件を壊さずに最も容易に拡張できる候補をベースに選ぶ。2 つが拮抗している場合は、Laziness Protocol に従い、より境界がクリーンな方、あるいは API が小さい方を優先する。

## Phase E: Graft

負けた各候補をもう一度たどり、ベースに移植する価値のあるものを探す。通常は候補ごとに 1〜2 個であり、ほとんどではない。各移植は第一原理から再設計しながら手作業で取り込み、結果が 1 つのメンタルモデルの下で一貫するようにする。機械的に貼り付けない。

候補が 1 つの形に収束した場合、それは強い合意である。収束を記し、そのコンセンサスの形を出荷する。移植は不要。大きく発散した場合は、Phase A の指定が不十分だったということである。発散を平均化するのではなく、再フレーミングして再実行する。

## Phase F: Verify

統合された成果物を、Prove It Works 原則(${CLAUDE_PLUGIN_ROOT}/skills/toshipon-mode/references/principles/prove-it-works.md)に従い、他の成果物と同じように検証する。検証で arena が捉え損ねた問題が見つかった場合、Phase A が誤っていた(再フレーミングして再実行)か、どれかの候補がそれを捉えていて移植を見逃した(Phase E に戻る)かのどちらかである。取り繕わないこと。

## Outputs

統合された成果物 1 つと、それに添える短い統合ノート。ノートには、ベースとその理由、cross-judge の判定、各移植とその出典候補、却下したものとその理由、収束や離脱があればそれ、検証結果を明記する。
