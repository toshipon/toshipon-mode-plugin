# Arena

同じタスクに対して N 個の並列試行をファンアウトする。すべての候補を最初から最後まで読む。最も強い候補をベースに選ぶ。他の候補から最良のアイデアを移植する。統合された結果を検証する。

## Start

何かを起動する前に、フェーズごとに 1 項目の todolist を開く。arena は自律的に走るので、このリストがフェーズを静かに取りこぼすのを防ぐ。

1. Frame
2. Fan out
3. Cross-judge
4. Pick
5. Graft
6. Verify

## Phase A: Frame

N 個の候補は同じプロンプトを受け取るので、プロンプトが契約である。何かを起動する前に正しく仕上げること。

1. 各候補が生成する成果物を明記する。
2. ルーブリックを導出する。*このタスク*における成功とは何かを述べ、それを 3〜6 個の具体的で採点可能な基準に落とし込む。具体的: `--dry-run フラグを追加し、書き込みをスキップする`。曖昧: `コードが正しい`。ルーブリックは Phase D で picker が使う道具であり、候補にはタスクしか見せない。
3. runner を選ぶ。既定は Agent tool の `model` オプションで `opus`、`sonnet`、`haiku` に 1 つずつ。arena が複数の設計方針をカバーする場合はさらに多く起動する。ジャッジよりも生成量が問われる作業では、同じモデルを N 回起動してもよい。
4. 出力先を割り当てる。各候補は自分専用の場所(可能なら git worktree、それが無理なら `/tmp/arena-<slug>/candidate-<n>/`)に書き込む。N 個の候補が同じパスに書き込むのは共有可変状態であり、何かを直列化する前に出力先を分離すること。

## Phase B: Fan out

Agent tool で `subagent_type: "general-purpose"`、`run_in_background: true` を指定し、N 個のサブエージェントすべてを 1 つのメッセージで起動する。各サブエージェントには、タスク、共有グラウンディングへのパス、自分専用の出力先、成果物と短い根拠の両方を作成する指示を渡す。

根拠(rationale)は必須である。これがないと、親エージェントは候補の構造が原理に基づくものか偶発的なものか判断できず、Phase E での移植が信頼できなくなる。各根拠には、候補が検討した代替案と、何を却下したかを明記する。

候補が成果物を生成できなかった場合は、N-1 で続行し、統合記録にその離脱を記録する。

## Phase C: Cross-judge

Phase B のすべての候補が完了したら、`opus`、`sonnet`、`haiku` の中からジャッジのティアを選ぶ。ほとんどの runner が使ったティアとは異なるティアを優先する(異なるモデルファミリーの代わりに)。Agent tool でそのモデルの Explore サブエージェント(`subagent_type: "Explore"`)を 1 つ起動する。このジャッジはルーブリックとパスラベル付きの候補を見て、基準ごとに採点し、根拠付きでベースを推薦する。これは Phase D の親エージェントによる読み込みと並行して走るのであって、候補自体と並行するのではない。候補がまだ書き込み中にジャッジを起動すると、部分的あるいは空の出力を見て離脱と報告してしまう。

## Phase D: Pick a base

ベースを選ぶ前に、すべての候補を最初から最後まで読む。N 個の候補をざっと流し読みするだけでは、表面的に最も見慣れた候補しか浮かび上がらない。

全体的な印象ではなく、ルーブリックの基準ごとに各候補を採点する。cross-judge と比較する。ベースについての一致は選択の裏付けになる。不一致は、あなたか cross-judge のどちらかにバイアスがあるか、ルーブリックが曖昧だったことを意味する。決める前に両方の根拠を読むこと。

将来のメンテナが不変条件を壊さずに最も容易に拡張できる候補をベースに選ぶ。Laziness Protocol に従い、2 つが拮抗している場合はより境界がクリーンな方、あるいは表面積が小さい方を優先する。

選んだ候補とその理由を、ベースの成果物と並べて短い統合ノートに記録する。cross-judge の判定も含める。

## Phase E: Graft

負けた各候補をもう一度たどり、ベースに移植する価値のあるものを特定する。シグナルは通常、候補ごとに 1〜2 個であり、ほとんどではない。

各移植は手作業で、第一原理から再設計しながら取り込む。機械的に貼り付けない。結果は 1 つのメンタルモデルの下で一貫していなければならない。

何を、どの候補から移植したか、そして何を却下しどんな理由だったかを記録する。却下の記録は、この記録の中で最もシグナルが高い部分である。将来の読者は、あなたが何を残したかだけでなく、何を検討し捨てたかから学ぶ。

N 個の候補が同じ形に収束した場合、それは強い合意のシグナルである。記録に収束を記し、そのコンセンサスの形を出荷する。移植は不要。N 個の候補が大きく発散した場合は、Phase A の指定が不十分だったということである。発散を平均化するのではなく、再フレーミングして再実行する。

## Phase F: Verify

統合された成果物は、Prove It Works 原則(${CLAUDE_PLUGIN_ROOT}/skills/toshipon-mode/references/principles/prove-it-works.md)に従い、他の成果物と同じ精査に耐えなければならない。arena を使ったこと自体は合格の理由にならない。

検証で arena が捉え損ねた問題が見つかった場合、Phase A が誤っていた(再フレーミングして再実行)か、どれかの候補がそれを捉えていて移植を見逃した(Phase E に戻る)かのどちらかである。取り繕わないこと。

## Outputs

統合された成果物 1 つ。それに添える短い統合ノート 1 つ。ベース、移植した内容(出典候補付き)、却下した内容、離脱があればそれ、検証結果を明記する。
