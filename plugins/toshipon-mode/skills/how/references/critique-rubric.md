# Architectural Critique Rubric

関連するレンズだけを使ってレビューする。すべてのレンズがすべてのサブシステムに当てはまるわけではない。

## Abstraction Fit

抽象化はその存在価値に見合っているか?

- 各抽象は実在の概念を表しているか、それとも「いつか必要になるかもしれない」ための間接化レイヤーか?
- 境界は正しい場所にあるか? 独立して変化するものを分離できているか?
- コンポーネントが本来知る必要のない実装の詳細を共有してしまう、偶発的な結合はないか?
- ビジネスロジックはフレームワークの配線と絡み合っているか、それともきれいに分離されているか?

過剰な抽象化は、抽象化不足と同じくらい問題である。ドメインがシンプルなら、フラットでシンプルな設計で構わない。

## Data Model

データ構造は実際の利用パターンに合っているか?

- データモデルは実際のアクセスパターンに合わせて設計されているか、それとも概念的にモデル化された形のままか?
- インピーダンスミスマッチ、つまりモデルがアクセスパターンに合っていないためにコードが常にデータを組み替えている箇所はないか?
- 型は正直か? 実行時のデータの実際の姿を表しているか、それとも実際以上の構造を主張しているか?

## Boundary Discipline

システムの境界はきれいに、適切な位置に置かれているか?

- バリデーションはエントリーポイントに集中しているか、それとも内部コードに散在しているか?
- エラーは境界で処理されきれいに伝播しているか、それとも各層でキャッチして再スローされているか?
- データは型付けされた形で境界を越えているか、それともオプショナルフィールドの詰め合わせとして渡っているか?
- このサブシステムは単独でテストできるか、それともシステム全体を起動する必要があるか?

## Evolution Readiness

このアーキテクチャは、起こりうる変化にどれだけ耐えられるか?

- 最も起こりそうな次の要件が明日発生したら、どれだけ変更が必要か? 「1 ファイル」か「すべて」か?
- 緩和が必要になるハードコードされた前提はないか?
- この設計は後付け(あとから継ぎ足された)か、それとも統合されている(最初から計画の一部だったように見える)か?
- 誰も依存していない互換性のためだけに legacy パスが温存されていないか?

仮定上の変更に対応していないことを罰点にしない。コードベースの軌道から見て起こりうる変化に焦点を当てる。

## Complexity vs. Value

複雑さの予算は賢く使われているか?

- 複雑さは必要な部分(コアロジック、扱いにくい不変条件)に集中しているか、それとも偶発的な場所(ボイラープレート、不要な間接化、設定)にあるか?
- 同じ振る舞いをもっとシンプルに実現する方法はないか?
- すべてのコンポーネントは存在価値があるか、それとも以前の設計の名残がないか?

## Consistency

このサブシステムは、コードベースの他所で確立されたパターンに従っているか?

- 似た問題は、この場所でも他の場所と同じように解決されているか、それともこの領域が独自のパターンを発明しているか?
- パターンが異なる場合、正当な理由があるか、それとも単に独立して進化しただけか?
- 不整合は自動的に悪いわけではない。ただし説明のつかない不整合は保守負担になる。
