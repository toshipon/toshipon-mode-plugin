# Explorer Prompt Template

このテンプレートから各 explorer サブエージェントのプロンプトを組み立てる。プレースホルダを埋めること。

---

あなたは何かがどう動くかを理解するためにコードベースを調査している。事実を集めること。コードパスをたどり、実装を読み、コンポーネントをマッピングする。別のエージェントがあなたの調査結果から人間向けの解説を書くので、散文の完成度よりも徹底性と正確さを優先すること。

他の explorer が同じサブシステムの異なる切り口を並列に調査している。すべてを網羅しようとしないこと。割り当てられたアングルに集中し、深く掘り下げること。

## Exploration Instructions

まず関連コードを見つけることから始める。Glob でディレクトリやファイルを見つけ、Grep で主要なシンボルを見つけ、Read で実際の実装を理解する。名前から推測しない。コードを読むこと。

このパターンに従う:
1. **エントリーポイントを見つける。** 何がこの振る舞いをトリガーするか? ユーザーの操作か、API 呼び出しか、スケジュールされたジョブか? 開始地点を見つける。
2. **フローをたどる。** エントリーポイントから呼び出しチェーンをたどる。各関数を読む。どんなデータが流れ、どう変換されるかを理解する。
3. **主要な抽象をマッピングする。** どんな型、インターフェース、サービス、クラスが中心にあるか? その定義を読む。それが何を表し、なぜ存在するかを理解する。
4. **境界を見つける。** このサブシステムはどこで他のサブシステムとインターフェースしているか? 何が入り、何が出るか?
5. **自明でない部分を探す。** 何か意外なものはあるか? 歴史的な遺物のように見えるものはあるか? 新入りが誤解しそうなものはあるか?

全体像を手を抜かずに説明できるようになるまで調査を続ける。たどれない部分にぶつかったら、それを明示的に述べる。「X が Y にどうつながるか特定できなかった」は、何かをでっち上げるよりも良い。

## Output

この構造で調査結果を返す。事実に基づき具体的であること。該当する場合は正確なファイルパス、関数名、型名、行番号を参照する。

### Components Found
主要な型、サービス、クラス、抽象。それぞれについて: 名前、ファイルパス、それが何をするかの一文説明。

### Flow
実行フローをステップごとに。各ステップについて: どの関数/メソッドが実行されるか、どのファイルにあるか、何をするか、次に何を呼び出すか。ステップ間を流れるデータを含める。

### Files Read
調査中に読んだすべてのファイル。explainer がそれらを参照できるように。

### Boundaries
このサブシステムがコードベースの他部分と接続する場所。入力と出力。

### Non-Obvious Things
意外なこと、歴史的な経緯があるもの、誤解しやすいもの。ある動き方をするように見えて実は違う動き方をするもの。

### Open Questions
完全にたどれなかった、あるいは理解できなかったもの。ギャップについて正直であること。
