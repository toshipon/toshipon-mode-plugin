# How

「X はどう動くのか」という質問に答えるためにコードベースを調査する。サブシステムにオンボーディングするシニアエンジニアのレベルで、明快なアーキテクチャ解説を作成する。動くメンタルモデルを構築するのに十分な内容であって、注釈付きのソースコードではない。

2 つのモードがある:

1. **Explain**（既定）。コードベースを調査し、明快な解説を作成する
2. **Critique**。まず解説し、その後複数のモデルを起動してアーキテクチャ上の問題を独立に洗い出す

## Explain モード

### Step 1. 質問を理解し複雑さを評価する

ユーザーが何について聞いているのかをパースする:

- 「レートリミッターはどう動く?」→ サブシステム
- 「オンデマンド利用の課金はどう処理している?」→ 機能フロー
- 「認証サービスはどう構成されている?」→ アーキテクチャの概観
- 「ユーザーがフォームを送信したときに何が起きるか説明して」→ ランタイムのトレース

範囲を特定する。曖昧な場合は、調査に入る前に自分の最有力な解釈を述べる。聞き返さない。的外れなら、ユーザーが軌道修正してくれる。

**複雑さを評価してアプローチを決める:**

- **シンプル**（単一モジュール、小さなユーティリティ、「関数 X はどう動くか」のような狭い質問）: explorer エージェントは省略し、explainer が一度の調査で説明まで行う。Step 2b へ。
- **複雑**（複数ファイル・複数サービスにまたがるサブシステム、横断的な機能、アーキテクチャ全体の概観）: まず explorer エージェントを並列起動し、その後 explainer に引き継ぐ。Step 2a へ。

迷ったらシンプルな方に倒す。explainer が行き詰まれば、いつでも explorer を起動できる。

### Step 2a. 調査する（複雑な質問のみ)

質問を 2〜4 個の並列調査アングルに分解する。各 explorer が重複作業をしないよう、サブシステムの異なる切り口を割り当てる。「レートリミッターはどう動くか」の分解例:

- Explorer 1: データモデルと状態管理
- Explorer 2: リクエストパスと制御の適用
- Explorer 3: 設定とメトリクス基盤

適切な分解の仕方は質問次第。判断に委ねる。狭い質問なら explorer 2 人で十分。広いサブシステムなら最大 4 人まで。

すべての explorer を 1 つのメッセージで起動する:

- Agent tool の `subagent_type`: `"Explore"`
- Agent tool の `model`: `"sonnet"`

各 explorer には `references/explorer-prompt.md` の共通ベースプロンプトに加えて、自分の担当する切り口を明示した具体的な調査アングルを渡す。各 explorer は以下を行う:
- 広く始める: 関連ディレクトリを Glob で探し、主要な型・インターフェース・クラス名を Grep で探す
- 糸をたどる: エントリーポイントから呼び出しチェーン(呼び出し元、呼び出し先、データフロー、型定義)をたどる
- 実際のコードを読む。ファイル名から推測しない
- 入力から出力まで(あるいはトリガーから効果まで)の全経路を、手を抜かずに説明できるようになったら止める
- 意外なこと、自明でないこと、新入りが誤解しそうなことをメモする

各 explorer は構造化された調査結果を返す: 見つかったコンポーネント、たどったフロー、読んだファイル、自明でない事項。explorer 間で重複があっても構わない。explainer が突き合わせる。

その後 Step 3 に進む。

### Step 2b. 直接説明する(シンプルな質問)

調査と説明を一度に行う単一のエージェントを起動する:

- Agent tool の `subagent_type`: `"Explore"`
- Agent tool の `model`: `"opus"`

このエージェントは自分で調査(Glob、Grep、Read)を行い、そのまま解説を書く。コミュニケーションスタイルと出力フォーマットは `references/explainer-prompt.md` を参照する。構造は同じで、explorer の調査結果を入力として持たないだけ。

Step 4 に進む。

### Step 3. 統合する(複雑な質問のみ)

すべての explorer から結果が返ったら、単一のエージェントを起動してそれらの調査結果を 1 つの一貫した解説に統合する:

- Agent tool の `subagent_type`: `"Explore"`
- Agent tool の `model`: `"opus"`

explainer はすべての explorer の調査結果を受け取り、人間向けの解説(下記の出力フォーマット)を書く。プロンプトテンプレートの全体は `references/explainer-prompt.md` を参照する。explainer は重複する調査結果を突き合わせ、矛盾を解消し、各切り口を統一した全体像に織り込む。

### Step 4. 提示する

explainer の出力をユーザーに提示する。明確さのために軽く編集したり、会話からの文脈を加えたりしてもよいが、大幅に書き直さない。explainer の説明そのものが成果物である。

### 出力フォーマット

質問に合わせて調整しつつ、この構造に従う。すべての質問にすべてのセクションが必要とは限らない。

**Overview。** 1〜2 段落。それが何であり、何をし、なぜ存在するのか。読み続けるかどうかを判断できる分量。

**Key Concepts。** 重要な型、サービス、抽象。それぞれの簡潔な定義。網羅的である必要はなく、残りを理解するために必要なものだけ。

**How It Works。** 解説の中核。フローを歩く: 何がトリガーになるか、ステップごとに何が起きるか、データがどこへ流れるか、判断のポイントはどこか。疑似コードではなく散文で。具体的なファイルと関数を参照し、読者が実際に見に行けるようにするが、本当に必要な場合を除きコードブロックを大量に貼らない。

**Where Things Live。** 関連するファイル/ディレクトリの簡単なマップ。すべてのファイルではなく、この領域で作業を始めるのに必要なものだけ。

**Gotchas。** 自明でない、あるいは意外なこと。何かが妙に見える理由を説明する歴史的経緯。既知の鋭利な角。

## Critique モード

ユーザーが理解だけでなく、アーキテクチャ上の問題・課題・改善点を求めたときに発動する。

### Step 1. まず説明する

上記の explain フロー全体(Step 1〜4)を実行する。批評する前に、そのアーキテクチャを理解していなければならない。

### Step 2. Critic を起動する

説明が完了したら、Agent tool を使い、ティアごとに 1 人ずつ(`opus`、`sonnet`、`haiku`)アーキテクチャ critic を単一メッセージで起動する。これらは最低限の reasoning レベルである。アーキテクチャの内容がより深い分析を要する場合は、各 critic のモデルを格上げしてよい。

各 critic について:
- Agent tool の `subagent_type`: `"Explore"`
- Agent tool の `model`: `"opus"` / `"sonnet"` / `"haiku"` のいずれか

プロンプトテンプレートは `references/critic-prompt.md` を参照する。各 critic には以下を渡す:
1. Step 1 で作成した解説(再調査させないため)
2. 関連ファイルパス(実際のコードを読めるようにするため)
3. `references/critique-rubric.md` のアーキテクチャ批評ルーブリック

### Step 3. リードとしての判断

interrogate スキルと同じフレームワーク。あなたは単なる集約者ではなく、実務的なリードである。

調査結果を分類する:
- **Act on**(対応する)。今すぐ直す価値があるアーキテクチャ上の問題
- **Consider**(検討する)。実在する懸念だが、コストとベネフィットが不明瞭
- **Noted**(記録する)。妥当な指摘だが優先度は低い
- **Dismissed**(却下)。誤り、文脈の欠落、あるいはスタイルの好みに過ぎない

まず(Step 1 の)解説を提示し、その下に批評の判定を提示する。解説はそれ単体で成立するべきで、単に仕組みを理解したいだけの人が批評まで読み進める必要はない。
