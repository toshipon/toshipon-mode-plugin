# Why

コードの背後にある動機と意図を調査する。なぜこう作られたのか? どんなエッジケースが考慮されたのか? どんなプロダクト・ビジネス・運用上の制約がこの設計を形作ったのか? どんな代替案が却下され、それはなぜか?

`how` スキルの相棒。`how` はコードが何をし、どう動くかに答える。`why` はどんな力がその形を生んだかに答える。

## How this skill works

歴史的な文脈は 7 つの証拠カテゴリに分散している: ソースコード管理履歴、issue/チケットトラッカー、長文ドキュメント、リアルタイムのチームチャット、インフラ観測基盤、エラー/例外トラッキング、プロダクト分析ウェアハウス。質問だけからどのカテゴリに答えがあるかを予測することはできないので、このスキルは実行時に利用可能な MCP を列挙し、それぞれをカテゴリにマッピングし、7 つすべてを並列に問い合わせ、その後明示的な確信度較正を伴って統合する。調査したカテゴリからの null 結果は、その意思決定がどう行われたかを示す一級の証拠であり、肯定的な発見と並べて報告すること。既定は最小限ではなく網羅性である。

## Operating Posture

慎重で、注意深く、精密な調査官として振る舞うこと。断片的な記録から歴史的な事件を組み立てる探偵のように考える。記録が薄いときはそう述べる。

具体的には:

- **物語より先に証拠。** まず断片を集め、それがどんな物語を支えるかを見る。物語を先に選んでそれに合う証拠をかき集めることは決してしない。
- **磨き上げより精密さ。** なめらかな言い換えより正確な引用と出典を優先する。読者はどんな主張も 1 分以内に出典までたどって検証できるべきである。
- **見ていないものを考慮する。** 見つかった証拠はサンプルであり、全真実ではない。結論を出す前に、もし別の説明が正しかった場合にどんな証拠が見えるはずかを問い、それを探したかを確認する。
- **ギャップに名前をつける。** 糸が途切れたら、ある情報源が検索不能だったら、ある問いに答えがなかったら、そのギャップを記録する。もっともらしく聞こえる推測で取り繕わない。
- **意図的にヘッジする。** 証拠が間接的なときは、その旨が言葉遣いに表れるようにする(「〜と思われる」「〜の可能性が高い」「〜を示唆する」)。確信度に合わせた言い回しは、統合者が上書きしてよいスタイルの選択ではなく、出力の機能である。
- **コードを読むことによる近道はない。** コードはそれが何をするかを教えるが、なぜ存在するかを教えることはめったにない。コードの形から意図を推測することに抗うこと。

この姿勢は免責事項ではなく、作業方法そのものである。

## Core Epistemics

このスキルは、断片化した歴史的証拠から**継ぎ接ぎの理解**を組み立てる。チケットは陳腐化する。チャットのスレッドは削除される。コミットメッセージは嘘をつく。PR の説明と実装の間で人は考えを変える。元の著者は会社を去っているかもしれない。

自分が知っていることと推測していることについて、徹底的に正直であること。目標は満足のいく物語ではなく、証拠を明るみに出し、確信度を較正し、ユーザーに判断を委ねることである。

原則:

- **すべてを引用する。** 意図についてのすべての主張は、特定のコミットハッシュ、PR 番号、チケット ID、ドキュメント URL、チャットのパーマリンク、あるいはコードコメントを参照すべきである。引用できないなら、それは事実ではなく推測であり、そう明示しなければならない。
- **「〜だから」より「〜のように見える」を優先する。** 証拠が間接的なときはヘッジする。確信を持った言い回しは直接的で明示的な証拠のために取っておく。
- **矛盾を明るみに出す。** 2 つの情報源が食い違う場合は両方を示す。自分の物語に合う方を静かに選ばない。
- **ギャップを認める。** どの情報源を調べても答えがない問いがあれば、そう述べる。正直な「なぜかは分からなかった」は、自信満々な当て推量に勝る。
- **複数の仮説が成立しうる。** 証拠が複数の物語に当てはまるときは、それぞれの証拠とともにすべて提示する。ユーザーに三角測量させる。
- **合理化に注意する。** 今日理にかなって見えるコードも、もはや当てはまらない理由で、あるいはそもそも大した理由もなく書かれたのかもしれない。意図を後付けしないこと。

確信度フレームワークとフレージングガイドの全体は `references/epistemics.md` を読むこと。統合者はこれに従わなければならない。

## Step 1. 対象と質問を理解する

ユーザーが何を求めているかをパースする。**対象**は通常、コードの塊、パターン、機能、あるいは名指しされた設計判断である。**質問**は通常、以下のいずれかである:

- 「なぜ X はこう設計されたのか?」設計の根拠。
- 「なぜ Y ではなく X をするのか?」トレードオフあるいは代替案。
- 「どんなエッジケースがこれを動機づけたのか?」防御的な理由。
- 「どんなビジネス・プロダクト上の制約がこれにつながったのか?」外部の強制要因。
- 「なぜこのコードはまだ存在するのか?」デッドコードの領域。
- 「X の歴史は?」広範な考古学的調査。

対象が曖昧な場合(明確な指示対象のない「なぜこのやり方をしているのか?」)は、会話の文脈(開かれているファイル、直近の編集、カーソル位置、直前に議論されたこと)から最有力の推測を行う。自分の解釈を簡潔に述べ、的外れならユーザーが軌道修正できるようにしたうえで進める。

## Step 2. コードのアンカーを確立する

investigator を起動する前に、調査を具体的なコードにアンカーする。以下が必要である:

- 関連するファイルパスと行範囲
- 主要なシンボル(関数名、クラス名、定数)
- 初期のコミットリスト。対象に触れた直近の数コミット。
- マージコミットからの PR 番号(subject line 内の `(#1234)` というパターン)

これはその場で構築する。安価であり、すべての investigator がこれを必要とする。

```bash
# 対象行を blame して最終変更コミットを特定
git blame -L <start>,<end> <file>

# リネームを追ってファイルの全履歴をパッチ付きで
git log --follow -p -- <file>

# ファイルに触れた直近 N 件のコミット。PR 番号が見える
git log --oneline -20 -- <file>

# コミットメッセージから PR 番号を抽出
git log -1 --format=%B <commit>
```

実質的な変更を伴うすべてのコミットについて、`gh` で PR の本文を取得する:

```bash
gh pr view <number> --json title,body,author,createdAt,mergedAt,labels,closingIssuesReferences,comments,reviews
```

これをシード文脈(ファイルパス、シンボル、コミット、PR 番号、紐づくチケット ID)として捉え、investigator に渡す。彼らが再発見せずに済むように。

## Step 3. investigator を並列に起動する(既定の姿勢)

**完全な並列調査を既定とする。** 各証拠カテゴリは異なる種類のシステムに存在し、質問だけからどのカテゴリに答えがあるかは見てみないと分からない。だから既定ですべてのカテゴリを並列に見る。

### Discovery

investigator を起動する前に、現在の環境で利用可能な MCP ツールと `gh` CLI を列挙し、それぞれを下記の 7 つの証拠カテゴリのいずれかにマッピングする。

1. ソースコード管理履歴
2. issue / チケットトラッカー
3. 長文ドキュメント
4. リアルタイムのチームチャット
5. インフラ観測基盤
6. エラー / 例外トラッキング
7. プロダクト分析ウェアハウス

ソースコード管理は git と `gh` を通じて常に利用可能である。他の 6 つについては、MCP 名、サーバーの指示、ツール名、リソース記述子を使って分類する。ある MCP が複数のカテゴリに当てはまりそうな場合は、その主要な証拠に合う方を選ぶ。曖昧なケースはカバレッジマップに記録する。

最小限ではなく、完全な**カバレッジマップ**を目指す。issue トラッカーからの null 結果は、その意思決定がチケット化されなかったことの証拠であり、それ自体が有用な事実である。null を記録すること。検索をスキップしないこと。

すべての一致する investigator を 1 つのメッセージで起動し、並行して走らせる。カテゴリごとに 1 investigator とすることで、各自が 1 つのツールのクエリ語彙と結果の形に特化できる。1 つのエージェントに複数の MCP をまたがせないこと。

各 investigator には以下を渡す:
1. `references/investigator-prompt.md` のベースプロンプト
2. 選ばれた MCP に対応する、`references/source-playbook.md` の例から適応させたカテゴリ別プレイブック `references/sources/<source>.md`
3. **対象コードが防御的に見える場合**(null チェック、リトライロジック、タイムアウト処理、レートリミッティング、フィーチャーフラグ、egress ガード、OOM ハンドラ)の横断的な `references/sources/incident-postmortem.md`
4. Step 2 のコードアンカー(ファイルパス、シンボル、コミットハッシュ、PR 番号、チケット ID)
5. ユーザーの元の質問

Subagent config(それぞれ):
- Agent tool の `subagent_type`: `"general-purpose"`(MCP ツールへのフルアクセスが必要なため。読み取り専用の Explore は使わない)
- Agent tool の `model`: `"sonnet"`(既定。掘り下げが必要な調査では `"opus"` に格上げしてよい)

investigator はそれでもリポジトリに何も書き込むべきではない。これはサンドボックスの話ではなく、姿勢の話である。

### Investigator roster。利用可能な証拠カテゴリごとに 1 人

一致する MCP を持つカテゴリごとに investigator を 1 人起動する。各自が正確に 1 つのツールまたは MCP を担当する。

各エントリは、そのカテゴリが物理的に何を含んでいるか、そしてそれが独自に明るみに出す「なぜ」の種類を記載する。カテゴリが空を返したときにギャップに名前をつける方法や、(まれな、証拠のあるスキップが妥当な場合に限り)スキップを正当化する方法を知るために使う。すべてのカテゴリは重複するが、それぞれが他が回収できない種類の証拠を担う。

1. **ソースコード管理の investigator。** git 履歴、PR 用の `gh`、コードコメント、テスト。常に起動する。唯一保証された情報源である。*レビュー時に記録された実装時の根拠*を明るみに出すのに最も長けている。問題を述べる PR の説明、代替案を議論するレビュースレッド、自明でない制約をエンコードするインラインコメント、動機となったエッジケースをエンコードするテスト名、チケットやインシデントにリンクするコミットメッセージ。出荷された diff に直接結びついているため最も信頼できる。

2. **issue / チケットトラッカーの investigator**(例: Linear、Jira、GitHub Issues、Plane、Shortcut の MCP)。チケット、プロジェクトドキュメント、ステータス更新、仕様の添付ファイル。*プロダクトあるいはビジネス上の強制要因*を明るみに出すのに最も長けている。顧客からの要求(「Acme が SOC2 監査のために X を必要としている」)、コンプライアンスの期限、親イニシアチブによる位置づけ(「Q3 エンタープライズ対応」)、チケットレベルのスコープ変更、動機を分類するラベル(`customer:*`、`incident-followup`、`compliance`、`perf-regression`)。理由がエンジニアリングの外部にある場合に最も強力。

3. **長文ドキュメントの investigator**(例: Notion、Confluence、Google Docs、Coda の MCP)。PRD、仕様、RFC、設計ドキュメント、ADR、ポストモーテム、チームページ、ミーティングノート。*長文の設計根拠*を明るみに出すのに最も長けている。問題提起、明示的な「検討した代替案」「却下したアプローチ」のセクション、優先順位を定める戦略ドキュメント、確定した決定を記した ADR、コードに直接結びつくポストモーテムのアクションアイテム。コードになる前に書き出された「なぜ」が置かれている場所。

4. **リアルタイムのチームチャットの investigator**(例: Slack、Discord、Microsoft Teams、Mattermost の MCP)。機能名やシンボルの検索、PR URL への言及、インシデントチャンネル(`#sev-*`、`#incident-*`)、出荷日周辺の著者ハンドルの活動。*ドキュメントに残らなかったリアルタイムの議論*を明るみに出すのに最も長けている。インシデント中の緊急対応の決定、PR の著者とレビュアーの間の Q&A、「Y だから X に決めた」というカジュアルなスレッド、PRD を必要としなかった小さな変更の根拠。ソースコード管理、チケット、ドキュメントの記録が薄いときに特に重要。

5. **インフラ観測基盤の investigator**(例: Datadog、New Relic、Honeycomb、Grafana、Splunk の MCP)。メトリクス、モニター、ダッシュボード、ログ、APM トレース、正式なインシデント。インフラ/ランタイムの視点。*コードを動機づけたインフラとランタイムの現実*を明るみに出すのに最も長けている。コードの定数と数値が一致するモニターの閾値、PR がマージされる直前の期間のメトリクススパイク、ポストモーテムのアクションアイテムとして作られたダッシュボード、対象を参照するインシデントのタイムライン。対象がインフラのシグナル(タイムアウト、リトライ、レートリミット、サーキットブレーカー)に反応している場合に最も強力。

6. **エラー / 例外トラッキングの investigator**(例: Sentry、Rollbar、Bugsnag、Airbrake の MCP)。issue、イベント、スタックトレース、リリース。*防御的あるいは修正的なコードを動機づけた具体的な例外とエラーの推移*を明るみに出すのに最も長けている。対象の関数を通るスタックトレース、PR の出荷日を挟む first-seen/last-seen ウィンドウを持つ issue、特定バージョンでエラーが止まったことを示すリリース相関。catch ブロック、null ガード、型チェック、リトライ、その他の防御に対して最も強力。

7. **プロダクト分析ウェアハウスの investigator**(例: Databricks、Snowflake、BigQuery、ClickHouse、dbt、Redshift の MCP)。プロダクト分析イベント、実験/フィーチャーフラグの露出テーブル、利用状況と課金イベント、クエリ履歴、ウェアハウステレメトリ。プロダクト/データの視点。出荷日周辺の*ユーザー行動とデータの現実*をカバーすることで、インフラ観測基盤を補完する。*コードを形作ったプロダクトとデータの現実*を明るみに出すのに最も長けている。機能利用の推移(ゼロからのステップ関数的な立ち上がりは、その PR がそれを世に出したことの強い証拠)、出荷判断に紐づく実験/フラグの露出データ、閾値定数の出所を明らかにする出荷前の分布(例: `limit = 128 * 1024` がアップロードサイズ列の p99 と一致する)、マイグレーション/バックフィルのデータパイプライン規模の証拠。フラグで制御されたコード、実験駆動の出荷、データマイグレーション、「この数値はどこから来たのか」という質問に最も強力。

### いつ investigator をスキップするか

**明示的で書面化された正当化**がある場合のみスキップする。それは最終的な「Sources Consulted」セクションに記載する。妥当な理由は 2 つ:

- この環境で**そのカテゴリに一致する MCP がない**。これは選択ではなくギャップとしてフラグを立てる。例: 「Real-time team chat skipped. No matching MCP available, so the conversational record was not searchable.」
- その情報源が**証拠のある形で無関係である**。「おそらく無関係」ではなく、それを裏付ける高い基準が必要。例: 「Error / exception tracking skipped. Target is a build-time script with no runtime code path.」であって「たぶんエラートラッキングには何もない、機能でありエラーではないから」ではない。

「純粋な機能コードだから、エラートラッキングには何もないだろう」は**十分ではない**。「長文ドキュメントには何もないだろう」も同様。検索を実行し、null 結果に語らせる。investigator が空で返るコストはサブエージェント 1 つ分。実在する設計ドキュメントを見逃すコストは誤った答えである。

スコープ評価の結果、PR の説明にすでに完全な答えが含まれている単一コミットの些細な対象であることが示唆される場合に限り、7 つすべての利用可能なカテゴリ検索が冗長であることを確認した**後にのみ**インラインで答えてもよい。その旨を明示的に述べること。これはまれであるべきである。

## Step 4. 統合する

統合者サブエージェントを 1 人起動する:

- Agent tool の `subagent_type`: `"general-purpose"`(引用のスポットチェックに MCP ツールへのフルアクセスが必要なため。読み取り専用の Explore は使わない)
- Agent tool の `model`: `"opus"`(既定。品質チェックとして引用の照合まで行う掘り下げが必要な作業のため)

統合者には以下を渡す:
1. investigator の調査結果。null 結果と、正当化付きでスキップされたカテゴリを含む
2. Step 2 のコードアンカー(ファイルパス、シンボル、コミットハッシュ、PR 番号、チケット ID)
3. ユーザーの元の質問
4. `references/epistemics.md` の確信度フレームワーク
5. `references/synthesizer-prompt.md` の統合者プロンプトテンプレート

その仕事は最終出力である: 確信度で重みづけされ、証拠が引用され、「分かっていること」と「推測していること」が明確に分離され、ギャップと null 結果の情報源が正直に認められたナラティブ。

## Step 5. 提示する

統合者の出力を受け取りユーザーに提示する。明確さのために軽く編集したり会話からの文脈を加えたりしてもよいが、**確信度の言い回しは書き直さない**。この確信度の枠組みそのものが成果物である。より権威的に聞こえるようヘッジを外すことは、このスキルが防ごうとしている失敗モードそのものである。

## Output Format

最終出力はこの構造を使う。必要に応じて調整するが、確信度の分離は維持すること。

**The Question**。ユーザーが尋ねたことを簡潔に再掲する。

**The Code in Question**。ファイルパス、行範囲、主要なシンボル。読者を方向づける 1〜2 行。

**What We Found (direct evidence)**。明示的な引用を伴う主張(PR 番号、チケット ID、ドキュメント URL、チャットのパーマリンク、コミットハッシュ、file:line 付きのコードコメント)。各箇条書きは、テキストによる証拠を持つ事柄である。現在形を使い、出典を引用または言い換える。

**What We Can Reasonably Infer**。どこにも明示的には述べられていないが、間接的な証拠や複数のシグナルの組み合わせによって十分に裏付けられている主張。各箇条書きは推論の連鎖を説明しなければならない: 「A と B から、C である可能性が高い」。ヘッジされた言い回し(「〜と思われる」「〜の可能性が高い」「〜を示唆する」)を使う。

**Competing Hypotheses**。証拠が複数の物語に当てはまるなら、それらを列挙する。記録が支持しないのに勝者を無理に決めない。それぞれについて、仮説、その証拠、反対の証拠を示す。(明確な答えがある場合はこのセクションを省く。)

**What We Don't Know**。明示的なギャップ。ユーザーが尋ねたが証拠が答えなかった質問。調べたが空振りだった情報源。具体的であること。「イシュートラッカーで 'rate limit' を検索したが、この特定の閾値を議論するチケットは見つからなかった」は「なぜかは分からない」より有用である。

**Sources Consulted**。investigator ごとに 1 行、何も見つからなかったものも含める。読者が一目で見えるべきこと: (a) どの MCP に問い合わせたか、(b) どれが空振りだったか、(c) どれがなぜスキップされたか。このカバレッジマップにより、ユーザーは網羅性を判断し、何か明らかなものが見逃されていれば軌道修正できる。

各行のフォーマット: `- <Source>: <what was searched>. <what was found, or "no relevant results," or "skipped. reason">.`

例:
- Source control (git/gh): `git log --follow backend/retry.ts`、PR #49074、#47812。PR #49074 が指数バックオフを導入し ENG-4421 にリンクしていることを発見。
- Issue tracker (Linear): "retry" と ENG-4421 を検索。ENG-4421 の親 issue は見つかったが、バックオフのパラメータについての議論は無し。
- Long-form docs (Notion): "retry policy"、"backend retries"、"ENG-4421" を検索。関連する結果なし。
- Real-time team chat (Slack): スキップ。この環境で一致する MCP が利用できない。ギャップ: 会話の記録は検索されていない。
- Infrastructure observability (Datadog): 2024-08-14 前後の `retry_count` メトリクスとモニターを検索。PR #49074 と同日に作成された "Upstream 5xx rate > 1%" モニターを発見。
- Error / exception tracking (Sentry): `retry.ts` を通るスタックトレースを持つ、2024 年 8 月に first-seen の issue を検索。PR の 1 週間前にスパイクしていた issue SENTRY-3821 を発見。
- Product analytics warehouse (Databricks): `<your_analytics_db>.<schema>.stg_backend_upstream_retry` を 2024-08-14 前後 30 日間で照会。エラー分類されたイベントの日次件数が PR 前の約 1,200 件/日から PR 後は 50 件/日未満に低下。`system.query.history` で関連するマイグレーションクエリも確認したが、該当なし。

Sources Consulted ブロックの後、ユーザーの `why` 質問が実際にこのコードを変更する前段階のものであれば、系譜の調査結果を、その変更を計画するのに適した Preserve / Change / Avoid / Risk の制約セットに変換する。

## Common Failure Modes to Avoid

- **自信満々のストーリーテリング。** 薄い証拠から組み立てられたもっともらしいナラティブ。出典のない箇条書きは「What We Found」ではなく「Inferred」か「Hypotheses」に入れる。
- **コード自体をその意図の証拠として引用すること。** 「null ケースをチェックしているから null ケースを処理する」は仕組みであって動機ではない。動機は外部の情報源(PR の議論、チケット、コメント、会話)から来るか、推測として明示されるべきである。
- **直近バイアス。** 最新のコミットが権威的だと決めつけること。現在の形は、しばしば多くの以前の決定の積み重ねである。さかのぼってたどること。
- **迎合的な同意。** ユーザーが理由を提案した場合(「これはパフォーマンスのためだと思うのですが?」)、それを仮説として扱い、独立に証拠を確認する。単に確認するだけにしないこと。
- **ギャップのセクションを省くこと。** 何が分からなかったかの正直な説明も、この出力の価値の一部である。
- **予測による investigator のスキップ。** 検索せずに事前に「長文ドキュメントにはおそらく何もない」「これはエラートラッキングの話ではない」と決めつけること。すべて 7 つを既定にする姿勢がこれを防ぐ。null 結果はデータポイントであり、スキップされた検索は盲点である。
- **investigator を 1 つのエージェントに統合すること。** 各 MCP は独自のクエリ語彙、結果の形、落とし穴を持つ。プールすると専門性が薄まり、カバレッジの判断が難しくなる。常にカテゴリごとに 1 investigator とすること。
