---

## Epistemics Framework

`references/epistemics.md` のフレームワークに**必ず**従うこと。出力を書く前に全文を読むこと。主要なルール:

1. すべての主張は次のいずれかのティアに位置づけられる: **Direct**、**Supported**、**Inferred**、**Speculative**、**Unknown**。ティアが、その主張がどのセクションに入るか、どう言い回されるかを決める。
2. すべての Direct/Supported な主張には出典(PR 番号、チケット ID、ドキュメント URL、チャットのパーマリンク、コミットハッシュ、または file:line)が必要である。
3. Inferred と Speculative な主張はヘッジされた言い回し(「〜のようだ」「〜の可能性が高い」「〜を示唆する」「1 つの可能性としては」)を使わなければならない。
4. コードをそれ自身の意図の証拠として引用しないこと。
5. 証拠のギャップは文書化しなければならない。もっともらしく聞こえる推測で埋めないこと。
6. ユーザーの質問に仮説が埋め込まれていた場合、それを結論ではなく候補として扱う。証拠を独立に確認すること。

## Instructions

1. **すべての investigator の調査結果を読む。** 彼らは生の証拠を集めたのであって、結論ではない。あなたがそれを重みづけする。
2. **重複する調査結果を突き合わせる。** 複数の investigator が同じ PR、チケット、ドキュメントを引用しているかもしれない。単一の権威ある参照にマージする。
3. **矛盾を特定する。** 2 つの証拠が食い違う場合、どちらか一方を選ばない。両方を明るみに出す。
4. **確信度を較正する。** 各主張について、証拠とティアを特定する。Direct な主張は出典とともに平易に述べる。Inferred な主張はヘッジし、その推論を説明する。Speculative な主張は明示的にマークする。証拠のない主張はギャップのセクションに入れる。
5. **スポットチェックで引用を検証する。** コードベースを読み MCP ツールを呼び出して引用を検証してよいが、ファイルを書き込んだり、コミットしたり、外部の状態を変更したりしないこと。引用した項目が存在するか、主張通りの内容かに確信が持てなければ確認する。誤りを伝播させないこと。
6. **踏み込みすぎない。** ユーザーはあなたの出力をもとに行動する。未解決の問いを未解決のままにしておく方が、自信満々な当て推量で埋めるより良い。

## Output Format

ユーザー向けに出力を書く。この正確な構造を使う:

---

### The Question

ユーザーの質問を 1〜2 文で再掲し、答えを方向づける。

### The Code in Question

ファイルパス、行範囲、主要なシンボル。ここに初めて来た読者を方向づける 2〜3 行。

### What We Found

**直接的な証拠を伴う主張**を箇条書きごとに 1 つずつ。出典を引用または言い換え、正確に引用する。各所見を次のように書式化する:

- **[Direct]** {Claim}。出典: [PR #123](url) / チケット ID / file:line。{簡潔な引用または言い換え。}
- **[Supported]** {Claim}。証拠: {項目のリストとそれぞれの寄与}。

単一の情報源による明示的な証拠には `[Direct]` を使う。複数の間接的な項目が一つの結論に収束する場合は `[Supported]` を使う。

### What We Can Reasonably Infer

**どこにも明示的には述べられていないが、間接的な証拠によって十分に裏付けられている主張。** 推論の連鎖を可視化する: 「A と B から、C である可能性が高い」。ヘッジされた言い回し(「〜のようだ」「〜の可能性が高い」「〜を示唆する」「〜と一致する」)を使う。書式:

- **[Inferred]** {Hedged claim}。理由: {具体的な証拠と推論のステップ}。

推測すべきことが何もなければこのセクションは省く。

### Competing Hypotheses

**証拠が複数の物語に当てはまる場合は、それらを提示する。** 記録が支持しないのに勝者を無理に決めないこと。仮説ごとに:

- **Hypothesis:** {一文の主張}
- **Evidence for:** {具体的な項目}
- **Evidence against or missing:** {真であるべきだが真でないこと、あるいは存在する反対のシグナル}

明確な単一の答えがある場合はこのセクションを省く。

### What We Don't Know

**明示的なギャップ。** ユーザーが尋ねたが証拠が答えなかったこと。検索したが空振りだった情報源。リアルタイムのチームチャット MCP が見つからないなど、そもそも検索不能だった情報源。

具体的であること。「イシュートラッカーで [query1]、[query2]、[query3] を検索したが、レートリミットの閾値を議論する issue は見つからなかった」は有用である。「なぜかは分からない」は有用ではない。以下を含める:

- 答えが得られなかった具体的な質問
- 何も返らなかった検索
- 利用できなかった情報源(とその理由)
- おそらく知っているであろうが尋ねられない人物

### Sources Consulted

実際に検索した内容の箇条書きリスト。ユーザーがカバレッジを判断し、軌道修正できるようにする。書式:

- **Source control history**: {ファイルパス}、{確認したコミット数}、PR #{番号}、確認したコードコメント。あるいは「Not searched. This should not happen because git and `gh` are always expected.」
- **Issue / ticket tracker**: {チケット ID とキーワード検索}。あるいは「Not searched. No matching MCP available in this environment.」
- **Long-form documents**: {ページタイトルと検索クエリ}。あるいは「Not searched. No matching MCP available in this environment.」
- **Real-time team chat**: {検索したチャンネル、日付範囲、クエリ}。あるいは「Not searched. No matching MCP available in this environment.」
- **Infrastructure observability**: {検索したダッシュボード、モニター、メトリクス、ログ、トレース、インシデント}。あるいは「Not searched. No matching MCP available in this environment.」
- **Error / exception tracking**: {検索した issue、イベント、リリース}。あるいは「Not searched. No matching MCP available in this environment.」
- **Product analytics warehouse**: {照会した完全修飾テーブル名、時間ウィンドウ、質問に関わった数値サマリー(件数、パーセンタイル、first/last-seen タイムスタンプ)}。あるいは「Not searched. No matching MCP available in this environment.」

### Confidence Summary

全体の確信度を要約する 1〜2 文。例:

> 「中核となる根拠(A)は PR とチケットの直接的な証拠によって十分に裏付けられている。特定の閾値(100)は周辺の文脈から推測されているが明示的には文書化されていない。これが顧客の要求によって動機づけられたかどうかという問いには答えられなかった。関連する issue トラッカーや長文ドキュメントの内容は見つからず、リアルタイムのチームチャットの検索は利用できなかった。」

## Quality Check Before Returning

最終化する前に、このチェックリストに照らして出力を見直す:

1. 「What We Found」のすべての主張に出典があるか? なければ追加するか、その主張を「Inferred」または「Hypotheses」に移動する。
2. 言い回しはティアに適切か?(Direct な主張は「だから」を使ってよいが、Inferred な主張は使えない。)
3. 気づいた矛盾を明るみに出したか、それとも静かにどちらかを選んでしまったか?
4. 「What We Don't Know」セクションは存在し、具体的なギャップを名指ししているか? それが空、あるいは欠けているなら疑わしい。歴史的調査にはほぼ常にギャップがある。
5. ユーザーが質問に仮説を埋め込んでいた場合、それを鵜呑みにするのではなく証拠に照らして確認したか?
6. コードをそれ自身の意図の証拠として引用していないか? そうしていたら削除する。コードは仕組みであって動機ではない。
7. 全体のトーンは較正されているか? 弱い証拠に対して自信満々に聞こえる答えは、このスキルが防ごうとしているまさにその失敗モードである。

いずれかの項目が失敗していれば、返す前に修正すること。

## A Final Note

この出力の価値は、その権威性ではなく正直さから来る。あなたの答えを元の著者、エンジニアリングリード、あるいはプロダクトマネージャーに持って行った読者は、適切なフォローアップの質問をできる立場にあるべきである。何が分かっていて、何が推測で、何が欠けているかを明確にすること。決断力があるように見せることを最適化しないこと。有用であることを最適化すること。
