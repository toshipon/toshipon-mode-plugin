# Jira Tickets

## What this source contains

- 機能、バグ、その動機を記述するチケット
- チケットに添付された仕様、Confluence へのリンク、スクリーンショット
- epic / 親子 / リンク（blocks、relates to）の関係（広いイニシアチブ → 具体的なチケット）
- コメント（明確化、スコープの変更、「なぜこれをやっているか」の根拠、レビュー結果の記録）
- 動機の種類を示すラベルとコンポーネント（例: `compliance`、`incident`、`perf`）
- ステータス遷移の履歴（いつ着手し、いつ完了したか）
- Remote issue link（GitHub PR、Confluence ページ）

Jira は、プロダクト / ビジネス / 監査上の文脈がしばしば存在する場所である。「監査で求められた」「規制対応の期限があった」という層。

## How to search it

Atlassian MCP（`getJiraIssue`、`searchJiraIssuesUsingJql`、`getJiraIssueRemoteIssueLinks` など）を使う。tool 名の接頭辞は環境で異なるので、起動時に列挙してから使う。認証が失敗したら、止めてギャップを報告すること。

1. **紐づくチケットから始める。** シードのコミットや PR がチケットキー（例: `PROJ-1234`）を参照していれば、まずそれを取得する。コメントと changelog を含む全体を読む。
2. **JQL で関連チケットを検索する。** `text ~ "<機能名>"`、`summary ~ "<シンボル>"` を投げる。複数の言い回しを試し、チームが英語以外でも書くなら両方の言語で検索する。
3. **チケットのツリーをたどる。** サブタスクにたどり着いたら、その親と epic を取得する。サブタスクは戦術的であり、epic がしばしば「なぜ」を持っている。
4. **Remote link をたどる。** Confluence ページや PR への外部リンクを取得し、長文ドキュメントの investigator に渡す。
5. **ラベル・コンポーネント・期限を確認する。** ラベルは動機のカテゴリを示唆する。期限は作業を締め切りに結びつけ、それがしばしば動機を明らかにする。

## What good evidence looks like here

- ビジネス上の問題を述べる description: 「監査で X の証跡を求められた」
- 決定を記録するコメント: 「アプローチ A は課金サービスに触れる必要があるため、アプローチ B を選ぶことに決めた」
- イニシアチブのようなタイトルを持つ epic
- 添付された仕様や Confluence リンク
- `compliance`、`incident-followup`、`perf` のようなラベル

## Common pitfalls

- **スコープドリフト。** PR が参照するチケットは、クローズ後に別のスコープで再オープンされたかもしれない。changelog 全体を読む。
- **機械的なテンプレート。** 「背景」欄が定型文で埋められていることがある。汎用的な文言はおそらく実質的な答えではない。
- **古いチケット。** 古いチケットはしばしば変更前の計画を反映している。日付を確認し、コードの出荷日と突き合わせる。
- **重複としてクローズされたチェーン。** 重複元の関係をたどり、正規のチケットまで戻る。
- **プロジェクトの権限。** チケットにアクセスできない場合、推測せずギャップとして記録する。

## What to return

関連するチケットごとに:
- チケットキーとタイトル
- description またはコメントから引用した問題 / 動機（言い換えではなく正確なテキスト。統合者が引用するために必要）
- ラベル、epic、コンポーネント
- 報告者、作成日、完了日
- チケットへの URL
