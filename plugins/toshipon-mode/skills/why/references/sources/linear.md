# Linear Tickets

## What this source contains

- 機能、バグ、その動機を記述する issue
- issue に添付されたプロジェクトドキュメント(しばしば PRD や仕様)
- 親/子 issue の関係(広いイニシアチブ → 具体的なチケット)
- issue へのコメント(明確化、スコープの変更、「なぜこれをやっているか」の根拠)
- 動機の種類を示すラベル(例: `compliance`、`customer-request`、`perf`)
- スコープの変更を説明するステータス更新
- 添付ファイルと紐づく GitHub PR

Linear は、プロダクト/ビジネス上の文脈がしばしば存在する場所である。「顧客 X が求めたからやっている」や「これは Q3 コンプライアンスイニシアチブのためだ」という層。

## How to search it

Linear MCP を使う。

1. **紐づくチケットから始める。** シードのコミットや PR がチケット ID(例: `ENG-1234`、`[BUG-567]`)を参照していれば、まずそれらを `get_issue` で取得する。コメントを含む issue 全体を読む。
2. **キーワードで関連 issue をリストする。** `list_issues` を機能名、主要なシンボル、ビジネス用語のテキスト検索で使う。複数の言い回しを試す。
3. **issue のツリーをたどる。** サブ issue にたどり着いたら、その親を取得する。サブ issue は戦術的であり、親がしばしば「なぜ」を持っている。
4. **プロジェクトドキュメントを読む。** issue がプロジェクトに属している場合、`get_project` を使い、添付ドキュメントを確認する。プロジェクトレベルのドキュメントは、仕様と根拠が最も捉えられやすい場所である。
5. **ラベルとマイルストーンを確認する。** ラベルは動機のカテゴリ(customer-request、incident-followup、compliance)を示唆する。マイルストーンは作業を締め切りに結びつけ、それがしばしば動機を明らかにする。

## What good evidence looks like here

- ビジネス上の問題を述べる issue の説明: 「顧客 Acme が SOC2 監査のために X を必要としている」
- 決定を記録するコメント: 「アプローチ A は課金サービスに触れる必要があるため、アプローチ B を選ぶことに決めた」
- イニシアチブのようなタイトルを持つ親 issue: 「Q3 Enterprise Readiness」や「Reduce Payment Failures」
- 添付された PRD や仕様
- `customer:acme`、`incident-followup`、`compliance`、`perf-regression` のようなラベル

## Common pitfalls

- **スコープドリフト。** PR が参照するチケットは、クローズされ、異なるスコープで再オープンされたかもしれない。履歴全体を読む。
- **機械的なテンプレート。** チームによっては「Why」セクションを必須にしているが、定型文で埋めていることがある。汎用的な文言(「ユーザー体験の改善」)はおそらく実質的な答えではない。
- **古いチケット。** 古いチケットはしばしば変更された計画のバージョンを反映している。日付を確認し、コードの出荷日と突き合わせる。
- **重複としてクローズされたチェーン。** 重複元の関係をたどり、正規のチケットまで戻る。
- **プライベートなワークスペースの内容。** issue にアクセスできない場合、推測せずギャップとして記録する。

## What to return

関連するチケットごとに:
- チケット ID とタイトル
- 説明またはコメントから引用された問題/動機(言い換えではなく正確なテキスト。統合者が引用するために正確なテキストが必要)
- ラベル、親 issue、プロジェクト
- 著者、作成日、クローズ日
- 利用可能であればチケットへのリンク
