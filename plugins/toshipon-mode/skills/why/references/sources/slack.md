# Slack Conversations

## What this source contains

- 問題と決定に関するリアルタイムの議論
- 緊急対応の決定がなされたインシデントチャンネル
- トレードオフが議論された設計に関する議論スレッド
- シニアエンジニアが答えたが、ドキュメントには残らなかった質問
- 何かが見直された理由を説明するマージ後の議論
- DM(通常は検索不可。それに応じてスコープを調整する)

Slack は、特にドキュメントを必要としない小さな変更について、*実際の*決定がなされた場所であることが多い。同時に最も儚い情報源でもある: スレッドは削除され、チャンネルはアーカイブされ、検索品質は時間とともに劣化する。

## How to search it

Slack MCP ツールは様々である。利用可能な Slack MCP を確認し、まずそのツールスキーマを調べる。`mcp_auth` が必要な場合がある。認証が失敗したら、止めてギャップを報告すること。

1. **著者で絞った検索。** PR のマージ日付付近における PR 著者からのメッセージ。スコープを大幅に狭められ、しばしば有力な情報が見つかる。
2. **機能名と主要なシンボルのキーワード検索。** 誤字やカジュアルな言い回しも含める。
3. **PR URL 検索。** Slack はレビューや議論の際にしばしば PR をリンクする。PR の URL(あるいは単に `/pull/<number>`)を検索する。
4. **エラー文字列検索。** コードが特定のエラーを処理する場合、そのエラー文字列を検索する。インシデントのスレッドが浮かび上がることが多い。
5. **チャンネルで絞った検索。** 有力なチャンネルに絞る:
   - `#eng-*`。エンジニアリングの議論
   - `#proj-*`。プロジェクトチャンネル
   - `#incident-*` / `#sev-*`。インシデントチャンネル
   - 担当チーム固有のチャンネル
   - 設計レビューチャンネル
6. **スレッドをたどる。** 関連するメッセージを見つけたら、スレッド全体を取得する。決定はしばしば返信の中にある。

## What good evidence looks like here

- トレードオフが明示的に議論されたスレッド(「A を使うつもりだったが B の方が...だから良い」)
- コードが防いでいるバグを説明するインシデントチャンネルのメッセージ
- レビュアーからの質問と、著者やリードからの権威的な回答
- 決定がなされたミーティングへの言及
- プロダクトマネージャーやカスタマー対応のエンジニアが顧客の要望を説明するメッセージ

## Common pitfalls

- **チャンネルの考古学的限界。** 保持ポリシーにより、非常に古いメッセージは消えていることがある。ある日付より前が見つからない場合、その保持期間の崖をメモする。
- **検索できない DM。** 多くの決定は検索不可能な DM で行われる。それらは見逃す。既知の限界である。
- **「決定」としての思いつきの冗談。** Slack はカジュアルである。「Lol just do the thing」はコミットの前にあったとしても決定ではない。よく検討された議論を探すこと。
- **単一メッセージでの文脈の崩壊。** スレッドがないと、単一のメッセージは文脈の中とは違って読める。常にスレッドを取得すること。
- **認証失敗。** MCP が認証されていない場合は止める。調査結果をでっち上げないこと。Slack が検索できなかったと報告すること。

## What to return

関連するスレッドごとに:
- チャンネル名
- パーマリンクまたはスレッド ID
- 参加者
- 議論の日付範囲
- 帰属付きの主要な引用(一語一句)
- 文脈: どのスレッド/インシデント/議論の一部だったか
