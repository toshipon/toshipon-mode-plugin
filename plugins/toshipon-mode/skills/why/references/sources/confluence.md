# Confluence Docs

## What this source contains

- 要件定義、設計書、RFC
- ADR やそれに相当する「決定と代替案」の表
- 設計レビューや定例の議事録
- ドメインの文脈を持つチームページ、運用手順書
- インシデントのポストモーテム、障害報告
- 規制対応や監査対応のマトリクス
- 優先順位を定める方針ドキュメント

コードになる前の「なぜ」は、長文の場所に置かれていることが多い。実質的な機能には、たいてい設計書か議事録がある。

## How to search it

Atlassian MCP（`searchConfluenceUsingCql`、`getConfluencePage`、`getConfluencePageDescendants`、コメント取得系）を使う。tool 名の接頭辞は環境で異なるので、起動時に列挙してから使う。

1. **CQL によるキーワード検索。** 機能名、シンボル、チケットキー、著者で検索する。**英語以外の本文、特に日本語・中国語などの分かち書きしない言語では、全文検索が取りこぼす**。ヒットが無いことを「ページが存在しない」の証拠にしない。
2. **ページツリーを走査する。** 対象チームのスペースの親ページから子ページの一覧を取り、タイトルで候補を絞る。CQL の null 結果はここで補う。
3. **候補ページの本文を取得する。** プレビューではなく全文を読む。根拠は文書の中盤に埋もれていることが多い。
4. **コメントを読む。** フッターコメントとインラインコメント。レビュー時の指摘と回答が決定の理由を持っていることがある。
5. **版を確認する。** ページは後から書き換わる。対象コードが書かれた時点の版と現行の版が違う可能性を、更新日とバージョン履歴で確認する。
6. **他の文書置き場も見る。** 設計資料がスプレッドシートや Word 文書で共有されていることがある。Google Drive などの MCP があれば、機能名で検索して本文を読む。

## What good evidence looks like here

- 対象コードの目的に一致する「背景」「課題」セクションを持つ設計書
- 「検討した代替案」「採用しなかった案」のセクション
- 対象コードを特定のインシデントの修正として名指しするポストモーテム
- 「Y だから X に決めた」と記録し、PR と同じ著者 / 日付範囲に結びつく議事録
- 規制の条項 ID と実装箇所を対応付けた統制マトリクス

## Common pitfalls

- **古いドキュメント。** 設計書は実装前に書かれ、更新されないことが多い。実際の PR と突き合わせること。
- **ドキュメントと現実のドリフト。** 設計書には「X をする」と書かれていても、コードは実際には Y をする。その乖離をフラグする。統合者がその矛盾を明るみに出す。
- **全文検索の取りこぼし。** 上記の通り。ツリー走査で補う。
- **リンクされていないドキュメント。** 最も関連性の高いドキュメントがどこからもリンクされていないことがある。ツリー走査とタイトル検索が助けになる。
- **複数のドラフト。** あるトピックに複数のページがある場合、確定版あるいは最も最近更新されたものを見つける。
- **アクセス制限されたページ。** ページにアクセスできない場合、ギャップとして記録する。

## What to return

関連するドキュメントごとに:
- タイトルと URL（ページ ID を含む）
- 著者と最終更新日、読んだ版
- 動機のテキスト（一語一句の引用）とセクションの位置
- 関連する紐づくページ（統合者が引用できるように）
- ドキュメントが確定版か下書きか
