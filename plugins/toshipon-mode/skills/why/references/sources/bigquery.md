# BigQuery Analytics

## What this source contains

BigQuery はアクセスログ、プロダクト分析、データパイプラインの層である。インフラ観測基盤を補完する。観測基盤はインフラ / ランタイムの視点、BigQuery はプロダクト / データの視点（どのリクエストがどれだけ来たか、どの機能が使われたか、閾値定数がどこから来たか）を持つ。

- **アクセスログ。** ロードバランサやアプリケーションのアクセスログを取り込んだテーブル。リクエスト単位の path、status、latency、client。
- **プロダクト分析イベント。** ユーザー行動: 機能呼び出し、送信、クライアント側から報告されたエラー。
- **業務データのスナップショット。** 注文や請求などの集計テーブル。「この上限値はどこから来たか」に答える分布が取れる。
- **dbt モデル。** 型付けされ重複排除されたテーブル。上流の変更はしばしば下流コードの変更を動機づける。

テーブル名とスキーマは組織やチームごとに異なる。名前を仮定する前に `INFORMATION_SCHEMA` で確認する。

## How to search it

SQL を実行できる BigQuery の MCP か `bq` CLI を使う。権限が無ければギャップとして記録する。

**クエリ前に方向感を掴む。**

```sql
SELECT table_name FROM `<project>.<dataset>.INFORMATION_SCHEMA.TABLES` WHERE table_name LIKE '%<keyword>%';
SELECT column_name, data_type FROM `<project>.<dataset>.INFORMATION_SCHEMA.COLUMNS` WHERE table_name = '<table>';
```

**すべてのクエリを時間で区切る。** テーブルは巨大で、スキャン量が課金とタイムアウトに直結する。パーティション列（`_PARTITIONTIME` や日付列）を、出荷日を挟むウィンドウ（通常前後 30 日程度）でフィルタする。1 クエリのスキャン量に上限がある環境では `SELECT *` を避け、必要な列だけ選ぶ。dry run でスキャン量を先に見積もれる。

**集計で返す。** 生の行をダンプせず、日次件数、パーセンタイル、first / last-seen を返す。

### Investigation patterns that tend to pay off

1. **リクエストやイベントの推移。** PR マージ前後 ±30 日の日次件数。マージから 1〜2 日以内にゼロから安定した水準へのステップ関数的な立ち上がりは、その PR が機能を出荷したことの強い状況証拠になる。ゼロへの減衰は廃止を示唆する。
2. **ガードレール / 閾値の由来。** PR の前 14 日間における関連列の分布（中央値 / p99 / 最大値）。p99 が対象の閾値定数と一致する場合、その数値がデータから選ばれたことを示唆する。
3. **エラー分類の推移。** 5xx や特定のエラーコードを含むリクエストの日次件数が、防御コードの PR の後の数日でほぼゼロに落ちる。その PR がそのエラークラスを解決したことを示唆する。
4. **dbt lineage。** 対象が dbt モデルから読み書きしている場合、そのモデル自身の git 履歴がしばしば根拠を持つ。そのリードを git の investigator に渡す。

## What good evidence looks like here

- 対象の PR 出荷日を境にした明確なステップ変化
- 閾値定数と一致する出荷前の分布統計
- 対象のエンドポイントに対する特定 client からのアクセスパターン（レートリミットや allowlist の由来）

## Common pitfalls

- **計測されている ≠ 原因である。** イベントが存在するのは誰かがそれを記録する価値があると考えたからであり、対象コードがそれが原因で存在するとは限らない。因果を主張する前に、git investigator からの PR / コミットの引用と組み合わせること。
- **サイレントな計測変更。** 件数のステップ関数は、ユーザー行動が変わったのではなく、新しいログの記録が始まっただけかもしれない。同じウィンドウ内に計測用の PR がないか確認する。
- **取り込み遅延。** 外部ストレージからの同期やストリーミング取り込みには遅延がある。直近の時間帯のゼロは「無い」ではなく「まだ届いていない」かもしれない。
- **保持期間の崖。** 該当ウィンドウがテーブルの保持期間より前なら、それはギャップであって null 結果ではない。明示的に名指しする。
- **権限とスキャン上限。** クエリが権限やスキャン上限で失敗したら、結果をでっち上げず、実行できなかったクエリと理由を返す。

## What to return

関連する発見ごとに:
- 種類（アクセスログ / プロダクトイベント / 業務データ / dbt モデル）
- 完全修飾テーブル名と実行した正確なクエリ
- 照会した時間ウィンドウ
- コンパクトな数値サマリー（件数、パーセンタイル、first / last-seen）。**生の行をダンプしないこと。**
- 対象の出荷日との時間的相関（例: 「最初の行 2024-08-15; PR #49074 merged 2024-08-14」）
- 関連性と強さ: direct / circumstantial / weak
