# Datadog Telemetry

## What this source contains

Datadog は計画・議論されたことではなく、本番環境で実際に何が起きたかというランタイムの記録を保持している。

- **Metrics。** チームが計測したカウンター、ゲージ、ヒストグラム。あるメトリクスの*存在自体*が証拠である。誰かがこの数値を監視する価値があると考えたということだから。
- **Monitors & alerts。** チームが誰かを叩き起こすに値すると判断した条件。`rate_limit_hit > 10/min` で発火するモニターは、チームがその閾値を懸念していた直接的な証拠である。
- **Dashboards。** キュレーションされたビュー。そのチャートは、チームがそのサブシステムにとって何を重要と考えているかを教える。
- **APM traces & spans。** リクエストレベルのランタイムデータ。「なぜこれは遅いのか」「なぜここにタイムアウトがあるのか」という問いに有用。
- **Logs。** 大量のイベント記録。しばしば防御コードを動機づけたエラー条件を含む。
- **Incidents。** タイムラインと紐づくポストモーテムを持つ正式なインシデント記録。
- **Notebooks。** 探索的な調査。しばしば仮説と分析を含む。

Datadog は「このコードが書かれた頃の本番環境の現実はどうだったか?」という問いに答え、それがコードの形をしばしば説明する。

## How to search it

Datadog MCP を使う。広く始め、それから絞り込む。

1. **担当サービスを特定する。**

   ```
   search_datadog_services (名前やチームでフィルタ)
   search_datadog_service_dependencies (上流/下流を見る)
   ```

2. **まずダッシュボードとモニター。チームが何を気にかけているかを教える。**

   ```
   search_datadog_dashboards (query: 機能名、サービス名、シンボル)
   search_datadog_monitors   (同じクエリ)
   ```

   ダッシュボードやモニターが対象をカバーしていたら、そのクエリと監視している閾値をメモする。その閾値は「なぜ N でクランプされているのか」への答えであることが多い。

3. **対象周辺のメトリクス。**

   ```
   search_datadog_metrics (名前パターンで、例えば機能名やシンボル)
   get_datadog_metric_context (メタデータ: 説明、単位、タグ)
   get_datadog_metric (時系列; 「PR の日付付近でスパイクがあったか?」)
   ```

   メトリクスの推移と対象の追加/変更日を相関させることは強い裏付け証拠になる: 「`payment_timeout` メトリクスが 2023-11-03 にスパイクし、リトライロジックが 2023-11-06 にマージされた。」

4. **ログ。絞り込む、ダンプしない。**

   ```
   search_datadog_logs (対象付近の生ログパターン。use_log_patterns=true を設定)
   analyze_datadog_logs (SQL 風の集計。件数が必要なときのみ)
   ```

   シンボル、エラー文字列、機能名で検索する。**時間で区切ったクエリを強く優先する**(例: 変更前後 30 日)。ログ量は膨大であり、制約のない検索は時間を浪費し、タイムアウトすることがある。

5. **APM スパンとトレース。**

   ```
   aggregate_spans    (統計: 「このエンドポイントはどれくらいの頻度で失敗するか?」)
   search_datadog_spans (個々のスパンを調べる)
   get_datadog_trace  (特定のトレース ID)
   ```

   タイムアウト、リトライ、遅いパス、サービス間の振る舞いに有用。

6. **Incidents。**

   ```
   search_datadog_incidents (タイトル、チーム、日付範囲で)
   get_datadog_incident     (特定インシデントの詳細)
   ```

   対象が防御的に見える場合は、それが追加された頃のインシデントを検索する。タイムラインに「X に対する防御チェックを追加」を含むインシデント記録はほぼ直接的な証拠である。

## What good evidence looks like here

- コードが強制する制約と一致するクエリと閾値を持つモニター(コードは 100 にクランプ; モニターは 100/分を超えるとアラート)
- 対象の著者によって作られたダッシュボードで、コードが測定あるいは防御している内容に対応するウィジェットを持つもの
- コードがマージされる直前に本番環境のスパイクを示し、その後安定した値を示すメトリクス
- 対象コード、同じシンボル、あるいは同じエラー文字列を参照するインシデント記録
- 防御コードが防ごうとする特定のエラーパターンを示し、変更前のウィンドウでタイムスタンプされたログ

## Common pitfalls

- **相関は因果ではない。** PR 前のスパイクと PR 後の安定化は示唆的ではあるが決定的ではない。同じウィンドウに別の変更が入ったかもしれない。近隣の PR を確認すること。
- **見つけたチャートへの過剰適合。** Datadog の可視化は人間が*作った*ものであり、その人間のフレーミングを反映する。「retry success rate」という名前のチャートは、チームがリトライの成功を気にかけていた証拠であって、特定の行のコードが存在する理由の証拠ではない。
- **消えたテレメトリ。** メトリクスは名前が変わったり、削除されたり、保持期間が短かったりする。該当ウィンドウのデータが見つからない場合、それは null 結果ではなくギャップである。
- **スケールでのノイズ。** 一般的な文字列でログを検索すると数千件の一致が返る。サービス、タグ、時間で積極的に絞り込む。生ログをダンプするのではなく `analyze_datadog_logs` で集計する。
- **計測されている ≠ 原因である。** メトリクスの存在は、誰かが何かを測る価値があると考えたことを教えるだけであり、コードが*それが原因で*追加されたことを教えるものではない。コミット/PR の日付と突き合わせること。

## What to return

関連する項目ごとに:
- 種類(dashboard / monitor / metric / log pattern / trace / incident / notebook)
- タイトルまたは名前
- リンクまたは識別子(dashboard ID、monitor ID、metric name、incident ID)
- 所有者/著者、作成/更新日
- 質問に関わる具体的な条件、クエリ、引用(可能な限り一語一句)
- 関連性: これが対象コードについて何を示唆し、その結びつきがどれだけ強いか
