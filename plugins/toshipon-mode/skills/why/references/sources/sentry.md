# Sentry Error History

## What this source contains

Sentry は問題が起きたことのアーカイブである。防御的、修正的、あるいはエラーハンドリングのコードについて、しばしば直接的な動機を保持している: チェック、キャッチ、リトライ、フォールバックを追加する決め手となった特定の例外、スタックトレース、頻度。

- **Issues。** 件数、first/last seen タイムスタンプ、影響を受けたリリース、コメントとともにグループ化されたエラー
- **Events。** issue 内の個々のエラーインスタンス(スタックトレース、タグ、ユーザーコンテキスト)
- **Releases。** issue に紐づくデプロイ記録(「どのバージョンでこれが修正されたか?」に有用)
- **Replays。** ユーザー向けエラーのセッション録画(有効な場合)
- **Profiles。** パフォーマンスプロファイリングデータ(「なぜ」にはあまり有用ではなく、「どれくらい遅いか」向け)
- **Issue comments & assignments。** ときに根本原因についてのエンジニアのメモを含む

Sentry が提供する最も価値のあるものは**時間的相関**である: 「issue X は 2024-01-02 に作成され、500 件/日でピークに達し、防御チェックを出荷したリリース v2.14.0(2024-01-15)の後は現れなくなった。」

## How to search it

Sentry MCP を使う。

1. **方向感を掴む。** プロジェクトの slug と組織が分からない場合:

   ```
   find_organizations
   find_projects
   ```

2. **対象に関連する issue を検索する。**

   ```
   search_issues (自然言語で。例: "errors in PaymentService timeout", "unhandled exceptions in uploadFile")
   ```

   良いクエリの構成要素: 対象が扱う例外クラス名、対象の関数やクラスの名前、対象がチェックするエラーメッセージ文字列、対象のファイルパス。

3. **リリースと時間ウィンドウで絞り込む。**

   ```
   search_issue_events (release, time, environment, trace ID, tags でフィルタ)
   get_issue_tag_values (issue について、バージョン、ユーザー、環境ごとの分布を見る)
   ```

   疑わしい issue について、以下を確認する:
   - **First seen。** そのエラーはいつ現れ始めたか?
   - **Last seen。** いつ止まったか? 対象の出荷日と一致するか?
   - **Affected releases。** どのバージョンで見られたか? どのバージョンで修正されたか?
   - **Frequency trajectory。** スパイクした後、解決されたか?

4. **完全なイベントを取得して文脈を得る。**

   ```
   get_sentry_resource (Sentry の URL、または type+ID を渡す)
   ```

   スタックトレースは対象コードを通っているか? タグとブレッドクラムは対象が防御している条件と一致するか?

5. **対象の近くに出たリリースを確認する。**

   ```
   find_releases (対象のコミット日付付近)
   ```

   リリースバージョンを PR のマージ日と突き合わせる。

6. **Seer は控えめに使う。**

   ```
   analyze_issue_with_seer
   ```

   Seer は AI による根本原因分析を生成する。仮説を生成する道具として有用だが、権威的な証拠ではなく推論として扱う。実際のイベントとスタックトレースが一次証拠であり、Seer のナラティブは二次的なものである。

## What good evidence looks like here

- **first seen** が対象の PR の直前で、**last seen** がその直後である issue。対象がこのエラーに対応したことを示唆する
- 対象の関数を通る、あるいはそこに着地するスタックトレースで、正確な障害モードを示すもの
- PR の著者による修正内容を説明する issue へのコメント
- Sentry の issue の URL や ID を参照する対象の PR の説明あるいはコミットメッセージ
- 対象を含むリリースの後で止まる、高い件数を持つ issue

## Common pitfalls

- **グルーピングのドリフト。** Sentry はフィンガープリントでエラーをグループ化する。リファクタや名前変更は、「同じ」エラーを新しい issue ID の下で追跡させることがある。issue が突然終わっている場合、そのエラーは単に再グループ化されただけかもしれない。直後に新しい issue が現れていないか確認する。
- **リリース相関はノイジー。** リリースには多くのコミットが含まれる。issue が v2.14.0 で止まったことは、対象がそれを修正したことを証明しない。同じリリース内の別の変更が原因かもしれない。対象の正確なコミットと突き合わせること。
- **サイレントな修正。** エラーが止まるのは、防御コードのためではなく、上流が変わったためかもしれない。相関は修正を示唆するが、それを著者づけるものではない。
- **Resolved ≠ fixed。** issue はコードの変更なしに手動で「resolved」とマークされうる。`resolved` を人間によるマーカーとして扱い、コードが修正した証拠としては扱わないこと。
- **Seer の幻覚。** Seer は正しくない自信満々な説明を生成することがある。主張をする際は実際のイベント、スタックトレース、タイムスタンプに立ち返ること。
- **サンプリング。** 一部のプロジェクトはイベントを積極的にサンプリングしている。件数が少ないのは単に高いサンプリング率のためであり、稀なエラーとは限らない。疑わしければギャップとして記録する。

## What to return

関連する issue ごとに:
- issue ID とタイトル
- プロジェクトと組織
- first seen / last seen タイムスタンプ
- イベント件数(サンプリング率が分かればそれも)
- 影響を受けたリリース
- 対象との関連性を示す代表的なスタックトレースの抜粋(要約ではなく一語一句)
- 対象の出荷日との first/last-seen 相関
- issue へのリンク
- 著者のコメントや解決に関するメモ
