# Notion Docs

## What this source contains

- PRD(プロダクト要件ドキュメント)
- 技術仕様と RFC
- アーキテクチャ決定記録(ADR)
- 設計レビューのミーティングノート
- ドメインの文脈を持つチームページ
- インシデントのポストモーテム
- 防御コードを説明しうるランブック
- 優先順位を定める戦略ドキュメント

Notion は、コードになる前の長文の場所に「なぜ」が置かれていることが多い。実質的な機能には、たいていドキュメントがある。

## How to search it

Notion MCP を使う。

1. **`notion-search` によるキーワード検索。** 以下を試す:
   - 機能名
   - 対象コードからの主要なシンボル/クラス名
   - 著者のハンドル(設計ドキュメントはコードより先に書かれることが多い)
   - エラー文字列やユーザーに見える用語
   - コードの出荷時期が分かっていれば時間で区切ったクエリ
2. **`notion-fetch` で候補ページを取得する。** プレビューではなく全文を読む。根拠は文書の中盤に埋もれていることが多い。
3. **バックリンクと子ページをたどる。** 設計ドキュメントには、検討した代替案、付録、実装ノートのためのサブページがしばしばある。
4. **関連するデータベースを確認する。** `notion-query-data-sources` と `notion-query-meeting-notes` は、その決定が議論されたミーティングノートを明るみに出すことがある。
5. **著者固有のスペースを検索する。** PR の著者が個人ノートブックを持っている場合(一部の会社では一般的)、コードに先立つ探索的な思考が含まれているかもしれない。

## What good evidence looks like here

- 対象コードの目的に一致する「Problem statement」や「Motivation」セクションを持つ PRD
- 「Alternatives considered」や「Rejected approaches」セクション
- 対象コードを特定のインシデントの修正として名指しするポストモーテム
- 「Y だから X に決めた」と記録し、PR と同じ著者/日付範囲に結びつくミーティングノート
- 非自明な内容で埋められた ADR テンプレート(status、context、decision、consequences)

## Common pitfalls

- **古いドキュメント。** 仕様は実装前に書かれ、更新されないことが多い。ドキュメントは変更された計画を記述しているかもしれない。実際の PR と突き合わせること。
- **ドキュメントと現実のドリフト。** 仕様には「X をする」と書かれていても、コードは実際には Y をする。その乖離をフラグする。統合者がその矛盾を明るみに出す。
- **定型文のテンプレート。** 一部の組織では「Why」セクションを必須にしているが、中身のない文言で埋められることがある。具体性を探す。
- **リンクされていないドキュメント。** 最も関連性の高いドキュメントがどこからもリンクされていないことがある。広いキーワード検索が助けになる。
- **複数のドラフト。** あるトピックに複数のドキュメントがある場合、確定版あるいは最も最近更新されたものを見つける。日付を確認する。
- **アクセス制限されたページ。** ページにアクセスできない場合、ギャップとして記録する。

## What to return

関連するドキュメントごとに:
- タイトルと URL
- 著者と最終更新日
- 動機のテキスト(一語一句の引用)、ページ/セクションの位置とともに
- 関連する紐づくページ(統合者が引用できるように)
- ドキュメントが確定版か下書きか
