# Incident & Postmortem Context

これは独立した情報源ではなく、**横断的なアングル**である。インシデントはしばしば防御コードを動機づける(「X の障害の後にこのチェックを追加した」)。そのため対象が防御的に見える場合(null チェック、リトライロジック、タイムアウト処理、レートリミッティング、フィーチャーフラグ)、利用可能なすべての情報源にわたってインシデント履歴を具体的に探すこと:

- **Notion**: 対象のファイル、機能、エラー文字列に言及するポストモーテムを検索する
- **Linear**: `incident`、`sev-*`、`postmortem-action-item`、`reliability` のラベルが付いたチケットを探す
- **Slack**: 対象コードが追加された日付付近の `#sev-*` と `#incident-*` チャンネルを検索する
- **Git**: 「fix for incident」「add defensive check」「revert」の後に「re-apply with...」が続くようなコミットメッセージは強いシグナルである
- **Datadog**: タイムラインを持つ正式なインシデント記録には `search_datadog_incidents`; ポストモーテムのアクションアイテムとして作られたダッシュボードとモニター
- **Sentry**: first-seen/last-seen ウィンドウが対象の PR 出荷日と一致する issue; 対象を通るスタックトレース
- **Databricks**: エラー条件を分類するプロダクト分析イベント(クライアント側から報告された失敗、ユーザーに見えるリトライイベントなど)は、しばしばインシデントのウィンドウでスパイクする。対象の PR が出荷された後にそのイベント件数が下がっていれば、Datadog/Sentry のシグナルがノイジーな場合でも、対象コードがユーザーに見える症状を解決したことを示す状況証拠になる。

インシデントへのリンクを見つけたら、ポストモーテムの全文を取得する。ポストモーテムには通常、コードの変更に直接結びつく「Action Items」セクションがある。複数の情報源が裏付け合う場合(Datadog のインシデント ID が Linear のチケットに現れ、それが Notion のポストモーテムに現れ、それが対象の PR にリンクする Slack のスレッドに現れ、さらに Databricks のエラーイベント件数が修正後に下がっている)、その証拠は特に強い。

コードの防御的な性格からインシデント駆動の由来がもっともらしい場合に時間をかける価値がある。防御的に見えないコードについてはスキップする。
