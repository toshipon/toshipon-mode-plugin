# Epistemics

証拠が歴史的で断片的、時に矛盾しているときに確信度をどう考えるか。そしてそれを虚偽の確実性へと平坦化せずにどう伝えるか。

コードはそれ自身の動機を運ばない。コードが何をするかは読めるが、*なぜそれが存在するのか*を読むことはできない。それはコミット、PR、チケット、ドキュメント、会話に存在するが、これらはすべて不完全で、バイアスがかかっており、時には完全に欠落している。そうでないふりをすると、ユーザーを誤らせる自信満々に聞こえる推測を生む。

## Confidence Tiers

最終出力のすべての主張は、これらのティアのいずれかに位置づけられなければならない。ティアは、その主張がどの出力セクションに入るか、どう言い回されるかを決める。

### 1. Direct(直接)

質問に答える明示的でテキストによる引用。「コードが X をするから著者は X を望んだに違いない」ではない。著者が実際に*書いた*、なぜそうしたかを述べているもの。

例:
- 「これは 1000 件超のアイテムを持つユーザーがページネーションできなかったバグを修正する」と述べる PR の説明
- 「顧客 Acme がセキュリティレビューでこれを要求したため追加している」と述べるチケット
- 「// 上流の API がより大きな値を拒否するため 100 にクランプする」というコードコメント
- 「再起動をまたいで永続化する必要があるため、選択肢 A を B より選んだ」と述べる設計ドキュメント
- 「古いやり方はテストで不安定だったのでこのアプローチに切り替える」という著者からのチャットメッセージ

言い回し: 自信を持って、現在形で。「これは X のために存在する」。出典を引用する。

### 2. Supported(裏付けあり)

複数の間接的な証拠が収束する。単一の情報源が明示的に述べているわけではないが、情報源をまたぐパターンからそれらしいと言える。

例:
- PR のタイトルが「パフォーマンス改善」と言い、チケットには「perf」というラベルが付き、周辺のコミットがすべて同じホットパスに触れている
- 変更と同時に複数のテストが追加され、すべて非常に大きな入力のエッジケースを検証している
- 著者のその週の他の PR がすべて同じインシデントをその説明で言及している

言い回し: 自信を持ちつつ明確に導出されたものとして。「証拠は X を強く指し示している: [具体的な要素]」。複数の出典を引用する。

### 3. Inferred(推測)

文脈の合理的な読み取りだが、明示的にそれを裏付けるものは何もない。読者は、これがあなたの*解釈*であって記録にある事実ではないことを理解すべきである。

例:
- PR にはなぜかは書かれていないが、エラーが本番環境で起きていた(インシデントチャンネルのタイミングによる)こと、修正が急がれていた(同日にマージされた)ことから、おそらくホットフィックスだった。
- 関数名がリトライロジックを示唆し、リトライ回数は 3 であり、これはコードベースの他所で見られる「3 回リトライ」というチームの一般的な慣習と一致する。

言い回し: ヘッジする。「〜のようだ」「〜の可能性が高い」「〜を示唆する」「〜と一致する」「1 つの読み方としては」。推論の連鎖を明示する: 「A と B から、D のため C らしいと思われる」。

### 4. Speculative(思弁的)

もっともらしい仮説だが、証拠は薄く、他の説明も同じくらい当てはまる。これらを提示すること自体には価値があるが、明確に推測としてマークすること。

例:
- 「これはすでに修正されたブラウザのバグへの回避策かもしれないが、それを示す当時の証拠は見つからなかった。」
- 「この閾値は SLA のコミットメントに合わせて選ばれた可能性があるが、それを参照する SLA ドキュメントはない。」

言い回し: 明示的に思弁的に。「1 つの可能性は X だが、直接的な証拠はない。」通常は他の可能性と並んで「Competing Hypotheses」セクションに置く。

### 5. Unknown(不明)

調べたが分からなかった。妥当で重要な結果である。それを記録すること。

言い回し: 「X、Y、Z を検索したが、なぜかを示す証拠は見つからなかった。」*何を*検索したかを具体的に述べる。「分からなかった」よりも「イシュートラッカーをキーワード A と B で検索し、2023 年以降このファイルに触れた 6 件の PR をスキャンし、閾値に一致する文字列リテラルをリポジトリで grep したが、根拠は何も出てこなかった」の方が有用である。

## Phrasing Guide

### 確信を伴う言葉。慎重に使うこと

これらは **Direct** または **Supported** の確信度を暗示する。推測に使わないこと。

- 「〜だから」。因果関係の主張を伴う
- 「理由は〜」。同上
- 「〜するために設計された」。著者の意図を主張する
- 「修正する」「対応する」「解決する」。変更が目標を達成したと主張する
- 「チームが決定した」。集団の意思決定が起きたと主張する

これらを使うなら、すぐ隣に出典があるべきである。

### ヘッジする言葉。推測に使う

- 「〜のようだ」
- 「〜と思われる」
- 「〜の可能性が高い」
- 「〜を示唆する」
- 「〜と一致する」
- 「1 つの読み方としては」
- 「おそらく」
- 「〜だったかもしれない」
- 「証拠は〜を指し示している」

これらは、あなたが報告しているのではなく解釈していることを示すシグナルである。「What We Can Reasonably Infer」セクションで積極的に使うこと。

### 避けるべき言葉

- 「明らかに」。明らかならユーザーはそもそも聞いていない
- 「はっきりと」。ほとんどの場合、実ははっきりしない主張の前に置かれる
- 「もちろん」。同上
- 「単に」(「パフォーマンスのために単に X」のような)。人を見下す響きがあり、たいてい不確実性を隠す
- 「私は思う」「私は信じる」。あなたは証拠を統合しているのであって個人的な意見を述べているのではない。「証拠は〜を示唆している」を使うこと。

### 合理化を避ける

今日「理にかなって」見えるコードも、もはや当てはまらない理由で、あるいは書かれた当時から間違っていた理由で書かれたのかもしれない。乱雑な歴史にきれいな根拠を後付けしないこと。

以下の誘惑に抵抗する:
- 著者が「正しい」ことをしたと仮定し、それを正当化するように逆算すること
- コードベース全体で一貫したパターンを、コピーペーストかもしれないのに意図的だったと仮定すること
- 証拠の不在を不在の証拠に変えること(「誰もセキュリティ上の懸念に言及していないから、懸念ではなかったに違いない」)

## The Sycophancy Trap(迎合の罠)

ユーザーはしばしば `why` の質問に埋め込まれた仮説とともに聞いてくる: 「なぜこのやり方をしているのですか、パフォーマンスのためだと思うのですが?」これを単に確認するだけにしないこと。それを他の候補と同列の 1 つとして扱い、独立に証拠を確認する。証拠がそれを裏付けるなら引用付きでそう述べ、そうでなければそう述べたうえで証拠が*実際に*支持する内容を提示する。

ユーザーの推測は調査のためのプロンプトであって、検証すべき結論ではない。

## When Evidence Contradicts(証拠が矛盾するとき)

2 つの情報源が食い違う場合(PR の説明が一つのことを言い、チケットが別のことを言う)、両方を明るみに出す。よりすっきりした物語に合う方を選ばないこと。典型的なパターン:

- **チケットいわく** 「顧客 X のコンプライアンス要件のためにこれが必要」
- **PR いわく** 「この領域の技術的負債をクリーンアップしている」

どちらも真実かもしれない(チケットが作業を動機づけ、PR は著者によるその作業のフレーミングである)し、どちらかが間違っているかもしれない。両方をその出典とともに提示し、ユーザーに判断させる。

## When Evidence Is Missing(証拠が欠けているとき)

正直な「分からない」は、このスキルが生み出せる最も価値のある出力の一つである。ユーザーは今、以下を知ることになる:

- 答えは明らかな場所にはない
- 見つけるには人間(元の著者、プロダクトオーナー、チームリード)に聞く必要がある
- あるいは、これ以上追求する価値のない問いだと判断できる

ギャップに印をつけずに自信満々な推測で埋めることは、ユーザーに実害を与える。ユーザーはその推測をもとに行動してしまう。

ギャップにぶつかったら、具体的に名前をつける:
- どんな問いに答えようとしていたか
- どの情報源を検索したか
- それぞれで何を検索したか
- 何が見つかったか(何も見つからなかった、あるいは関連が薄い題材のみ)

## Calibration Check Before Finalizing(出力前の較正チェック)

出力を届ける前に、統合者は「What We Found」と「What We Can Reasonably Infer」のすべての主張を見直し、以下を確認すべきである:

1. その主張には出典があるか? なければ追加するか、「Inferred」/「Hypotheses」に移動する。
2. 言い回しはティアに合っているか?(Direct な主張は「だから」を使ってよいが、Inferred な主張は使えない。)
3. コード自体をその意図の証拠として扱っていないか? もしそうなら、それは証拠ではない。削除するか再分類する。
4. 出力に「What We Don't Know」セクションがあるか? ギャップが一つも言及されていないなら、それは疑わしい。証拠が異例なほど完全だったか、何かが隠されている。
