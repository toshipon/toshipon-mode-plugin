## PR Feedback

Pull Request のレビューコメントを効率的に対応し、エラー分析 3 段階アプローチで根本解決を図ります。

### 使い方

```bash
# レビューコメントの取得と分析
gh pr view --comments
「レビューコメントを優先度別に分類して対応計画を作成してください」

# エラー関連コメントの詳細分析
gh pr checks
「CI エラーを 3 段階アプローチで分析して根本原因を特定してください」

# 修正完了後の品質確認
npm test && npm run lint
「修正が完了したので回帰テストとコード品質をチェックしてください」
```

### 基本例

```bash
# コメント分類の実行
gh pr view 123 --comments | head -20
"レビューコメントを must/imo/nits/q に分類して対応順序を決めてください"

# エラー情報の収集
npm run build 2>&1 | tee error.log
"ビルドエラーの根本原因を特定し、適切な修正方法を提案してください"

# 修正実装の確認
git diff HEAD~1
"この修正がレビュー指摘事項を適切に解決しているか評価してください"
```

### コメント分類体系

```
🔴 must: 修正必須
├─ セキュリティ問題
├─ 機能バグ
├─ 設計原則違反
└─ 規約違反

🟡 imo: 改善提案
├─ より良い実装方法
├─ パフォーマンス改善
├─ 可読性向上
└─ リファクタリング提案

🟢 nits: 軽微な指摘
├─ タイポ修正
├─ インデント調整
├─ コメント追加
└─ 命名の微調整

🔵 q: 質問・確認
├─ 実装意図の確認
├─ 仕様の明確化
├─ 設計判断の背景
└─ 代替案の検討
```

### エラー分析 3 段階アプローチ

#### Stage 1: 情報収集

**必須実行**

- エラーメッセージの完全取得
- スタックトレースの確認
- 再現条件の特定

**推奨実行**

- 環境情報の収集
- 最近の変更履歴
- 関連ログの確認

#### Stage 2: 根本原因分析

- 5 Whys 分析の適用
- 依存関係の追跡
- 環境差異の確認
- 最小再現コードの作成

#### Stage 3: 解決策実装

- 即座の対処（ホットフィックス）
- 根本的解決（本質修正）
- 予防策（再発防止）

### 対応フロー

1. **コメント分析**: 優先度別の分類
2. **修正計画**: 対応順序の決定
3. **段階的修正**: Critical → High → Medium → Low
4. **品質確認**: テスト・リント・ビルド
5. **進捗報告**: 具体的な修正内容の説明

### 修正後の確認

```bash
# 基本チェック
npm test
npm run lint
npm run build

# 回帰テスト
npm run test:e2e

# コード品質
npm run test:coverage
```

### 返信テンプレート

**返信は指摘 1 件への回答なので、指摘を書くときと同じ 4 要素（引用・問題・根拠・修正）で書く。**
下書きを 1 行でも書く前にこの節を開く。「返信だからレビューではない」と判断しない。

**修正完了報告**

```markdown
> （レビュアーの指摘を原文引用。要約に置き換えない）

（指摘を認めるなら、何が起きるかを 1〜3 文。「抜けていました」で止めず結果まで書く）

**根拠**
- `VERIFIED` 確認したファイル・ID・コマンド出力を 1 行 1 事実で

**修正** （直した後の文そのもの、または diff）。[`<短縮SHA>`](https://github.com/<owner>/<repo>/pull/<number>/commits/<full-sha>)
```

**質問への回答**

```markdown
> （質問の原文引用）

（答えを先頭に 1 文で言い切る。「〜と考えています」で始めない）

**根拠**
- `VERIFIED` その答えの出どころ（該当箇所の引用）
```

確度ラベルは `VERIFIED`（自分で grep / read / 実行して確認）・`ASSUMED`（推測）・`UNKNOWN`（未確認）を
行頭にコード書式で置く。文中に埋めない。`ASSUMED` しか無いことは断定しない。

返信が 3 件以上あるときは、投稿前にユーザーへ提示する下書きの先頭に一覧表（コメント id・指摘・返信の主旨）を置く。

**修正コミットへの参照はリンクにする**

返信の末尾などで修正コミットを示すときは、SHA を裸で書かずに PR のコミット画面へのリンクにする。
短縮 SHA を表示名、完全な SHA を URL に使う（完全な SHA は `gh api repos/<owner>/<repo>/commits/<short> --jq .sha` で取る）。

```markdown
対応しました。[`7832fab3`](https://github.com/<owner>/<repo>/pull/<number>/commits/<full-sha>)
```

**レビュアーの提案した文面は、まずそのまま採る**

レビュアーが書き換え後の文面まで示した提案（`[imo]` `[want]` など）は、原則として**提案どおりに直す**。自分の書き方に作り変えない。

- 提案の弱点を自分の判断で補いたいときも、まず提案どおりに反映し、補いたい点は「〜も足すのはどうでしょう？」と質問の形で添える。返信の 1 文目を「〜だと〜ない」と提案の否定から始めない
- 提案を採らない場合は、採らない理由を 1 文で書き、相手に判断を委ねる（「この書き方でよいか見てもらえますか」で自分の案を通さない）

```markdown
<!-- NG: 提案を否定してから自分の案に差し替える -->
「必要に応じて」だと判定の基準が残らないので、条件を「〜」と書きました。この書き方でよいか見てもらえますか。

<!-- OK: 提案どおりに反映し、補いたい点は質問で添える -->
ご提案どおり「必要に応じて」を入れました。どの委託先が対象かは RCM 側で決まる想定ですが、本書にも条件を書いておいた方がよければ足します。
```

**技術判断説明**

```markdown
実装背景：[理由]
検討した代替案：[選択肢と判断根拠]
採用案の利点：[メリット]
```

### 返信を書く前に通す 3 つのゲート

下書きに**質問・相談を書きそうになったら、先にこのゲートを通す**。ここを飛ばすと、相手にしか聞けない事実ではないものまで質問として投げてしまい、返信を書き直すことになる。

#### ゲート 1: 「見つからない」と書く前に探索を尽くす

レビュアーが挙げた ID・文書名・出典が見つからないときは、**次を全部やってから**「見つからない」と書く。1 つでも残っていたら、それは未探索であって不在ではない。

```bash
# (1) 拡張子を絞らない — 台帳は .tsv / .csv / .puml / .yaml にあることが多い
git grep -I -n "<ID の数字部分>" <ref>
# (2) 既定ブランチだけでなく全リモートブランチを対象にする
for b in $(git branch -r --format="%(refname:short)" | grep -v HEAD); do
  git grep -I -n "<ID の数字部分>" "$b"
done
# (3) 相手の表記をそのまま使わない — 接頭辞が省略・追加されていることがある。
#     数字部分だけで引く（例: 指摘が "FOO-012-03"、実体は "BAR-FOO-012-03"）
```

リポジトリで出なければ Slack（`slack_search_public_and_private`）と Drive（`search_files`）も 1 回ずつ引く。
それでも出ないときだけ、**探した範囲を明記して** UNKNOWN と書く。

**読めないときも同じ扱いにする**。ファイルは見つかったのに中身が途中までしか返らない・読めないときは、取得手段を変えて読み切る（スプレッドシートは xlsx や CSV でエクスポートして対象の行を抜く、PDF はテキストを抽出する、チャットの添付はファイル本体を取得する）。手段を尽くす前に、中身をレビュアーやユーザーに尋ねない。

**手段を尽くしても開けない出典は、自分の出典として本文に足さない**。権限が無い・リンクが切れているなどで中身を読めなかった文書を、成果物の出典の欄や返信の「出典に足しました」に載せない。本文では「レビュアーのコメントによる」と出所を書き、返信では読めなかったこと（何で引いて何が返ったか）を 1 行添える。読んでいない文書を出典にすると、後から内容が食い違っても誰も気づけない。

#### ゲート 2: 質問してよいのは「相手しか知り得ない事実」だけ

| 書いてよい | 書かずに自分で決める |
| --- | --- |
| 社内の決定・契約・他チームの意図・原文の所在 | 書き方の選択（列挙 vs 規則、どちらが保守しやすいか） |
| 相手の指摘の意図が 2 通りに読めるとき | どの ID を正とするか・どちらを欠番にするか |
| 期限・優先度など相手の都合 | 要求文の表現・節の配置 |

相手が出典を示すだけのコメント（「〇〇の Q12 に記載」など）は、出典を開いて中身を読み、要求に何が言えるかまで自分で確かめてから返す。出典の中身は「相手しか知り得ない事実」に当たらない。

右列は**決めて、決めた結果と理由を 1 文**で書く。「どちらがよいでしょうか」「〜とも思いました」は右列に該当していないか確認する。

#### ゲート 3: 「列挙が足りない」指摘は列挙を直す前に列挙自体を疑う

レビュアーに「この一覧に X が入っていない」と言われたとき、X を足すだけで返すと同じ指摘が次も来る。

1. **機械判定できる規則**に置き換えられないか考える（例: ID の列挙 → 「特定の列に当該文書への参照を持つ行」という条件）
2. 置き換えたら、**規則で抽出した集合と元の列挙を突き合わせて差分を出す**（漏れが実在した事実は返信の根拠になる）
3. 規則に置き換えられないときだけ列挙を直し、返信に「次に増えたときの更新箇所」を書く

#### ゲート 4: 直した語・ID・値は、リポジトリ全体で横展開してから返信する

指摘された箇所だけを直すと、同じ誤りが兄弟の文書・別の章・図のラベルに残り、次の PR で同じ指摘が来る。返信を書く前に、直した文字列（誤っていた節番号・ID・用語・値）でリポジトリ全体を検索する。

```bash
# 直す前の文字列で全体を引く。0 件になるまで直すか、残す理由を返信に書く
git grep -n -F '<直す前の文字列>' -- . ':!*.png' ':!*.svg'
```

- 言い換えを取りこぼさないよう、ID は数字部分でも引く（ゲート 1 の (3) と同じ）
- 返信には「全体を検索して N 箇所を直した」と件数を書く。0 件だった場合も書く

#### ゲート 5: 「別 PR で直す」と返すなら、その場で追跡先に起こす

返信で後回しにした項目は、次の PR を書くころには忘れている。「別 PR で対応します」と書くときは、同じターンで追跡先を作る。

1. この PR の本文にチェックリスト（`- [ ] <指摘の要旨>（<コメントへのリンク>）→ <直す PR か issue>`）を足すか、issue を起こす
2. 返信にはその追跡先のリンクを書く
3. マージを提案する前に、未解決のスレッドと未消化のチェックリストが 0 であることを確かめる

```bash
gh api graphql -f query='query($o:String!,$r:String!,$n:Int!){repository(owner:$o,name:$r){pullRequest(number:$n){reviewThreads(first:100){nodes{isResolved comments(first:1){nodes{url body}}}}}}}' \
  -f o=<owner> -f r=<repo> -F n=<number> \
  --jq '.data.repository.pullRequest.reviewThreads.nodes[] | select(.isResolved|not) | .comments.nodes[0].url'
gh pr view <number> --json body --jq .body | grep -n -- '- \[ \]'
```

### 注意事項

- **優先度遵守**: Critical → High → Medium → Low の順で対応
- **テストファースト**: 修正前に回帰テスト確認
- **明確な報告**: 修正内容と確認方法を具体的に記述
- **建設的対話**: 技術的根拠に基づく丁寧なコミュニケーション
